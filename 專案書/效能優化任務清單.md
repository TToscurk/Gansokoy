## 任務 1：Shader 預編譯（先做，幾行程式碼）

**問題**：材質的 shader 是第一次被畫到才編譯，所以首次轉頭看到水面、光柱、
特效時會突然卡一下。

**做法**：每張圖在世界建構完成、loading 畫面還沒收掉之前，呼叫：
```js
await renderer.compileAsync(scene, camera);
```
有 composer 的圖（神社）連 labelScene 一起 compile。整合進 mapBootstrap
（或各圖的初始化尾端），讓之後的新圖自動有這個行為。

**驗收**：進圖後第一次快速轉一圈視角，不應該有肉眼可見的單幀卡頓。

---

## 任務 2：合併來源幾何體的記憶體審計

**問題**：village.js 有 69 個 `new THREE.XxxGeometry`、main.js 有 112 個。
mergeStaticByMaterial 把頂點烘進大網格之後，那些來源 mesh 的 geometry
如果沒有 dispose，同一份頂點資料在 GPU 記憶體裡存兩份。18 張圖的量級下
會差很多。

**做法**：
1. 檢查 src/core/optimize.js 的 mergeStaticByMaterial：烘完之後，
   來源 mesh 是否有從場景移除＋geometry.dispose()？
   （注意：多個 mesh 共用同一顆 geometry 的情況要用參照計數或 Set 去重，
   不能 dispose 到還在用的。）
2. 沒有的話補上；有的話，用 renderer.info.memory.geometries 在
   合併前後各印一次，確認數字真的有降。
3. 順手查 CanvasTexture：main.js 用 canvas 畫的重複貼圖，同樣圖案
   是否有重複建立多份 texture 的情況，有就共用單一實例。

**驗收**：每張圖 console 印 renderer.info.memory（geometries/textures）
合併前後對比，寫進 README 的效能段落。

## 任務 3：更新頻率 LOD（CPU 端節流）

**問題**：渲染有 LOD，但更新邏輯（NPC 走位、怪物 AI、里民路人）
看起來每幀全跑。低階機（Iris Xe 等級）CPU 端的 ms 佔比不小。

**做法**：
1. 給 NPC／路人的 update 加距離分級：
   - < 34m（跟現有 CHAR_LOD 門檻對齊）：每幀更新
   - 34–100m：每 3 幀更新一次（dt 累積後一次補）
   - > 100m：每 10 幀，或只更新位置不播動畫
2. 怪物的 aliveNear／目標搜尋：先用空間格子粗篩（pathnet 已經有
   格線查詢的基礎設施，同思路），不要每隻怪每幀掃全部玩家距離。
3. 天氣粒子在鏡頭後方的可以跳過位置更新（視錐外不更新，只在
   進視錐時補算）。

**驗收**：人間之里 52 位路人的場景，用 performance.now() 包住
update 迴圈量 CPU ms，前後對比寫進 README。

## 任務 4：低檔位改假陰影

**問題**：單張陰影貼圖蓋整張圖，圖越大每公尺解析度越低；
低檔位 1024 的陰影在大圖上會很粗。cel-shaded 卡通風其實不需要
所有物件都投真陰影。

**做法**：
1. 做一個貼地圓片假陰影系統：一個共用的радиальный漸層 CanvasTexture、
   一個 InstancedMesh，樹木／石頭／燈籠底下各放一片，尺寸跟物件半徑走。
2. 畫質「低」檔：關掉 sun.castShadow，全場只用假陰影。
3. 畫質「中／高」檔維持現狀（真陰影），但樹木這類量大的裝飾物
   可以考慮中檔也改假陰影、只留建築跟角色投真影——做 A/B 截圖
   給我看再決定。
4. 之後蓋大圖（youkaiMountain 560×560）時，評估要不要上 three.js
   的 CSM（級聯陰影）；先不要現在做，等大圖蓋出來有實際場景再測。

**驗收**：低檔位在 shadow pass 的三角形數對比；截圖 A/B 確認
卡通風格下視覺差異可接受。

## 任務 5：SPA 換圖重構（大手術，最後做，先決策再動工）

**問題**：location.href 換圖＝整個 WebGL context 丟掉重建：
黑屏讀取、每張圖重編譯所有 shader、跨圖狀態只能走 localStorage。

**做法（如果決定做）**：
1. 一個常駐 renderer/composer/玩家模型/HUD/Environment。
2. 每張圖改成 export 一個 build(world, ctx) 模組，換圖時：
   dispose 舊場景 → import() 新圖模組 → build → compileAsync → 淡入。
3. 舊的 maps/<id>/index.html 保留成「直接深連結到該圖」的入口
   （內部轉呼叫 SPA 帶參數），開發時單圖除錯的便利性不丟。

**先回答我這些再動工**：
- 現有 18 張圖的遷移工作量估計（每張要改多少）？
- progression.js / vitals 現在靠 localStorage 跨頁，改 SPA 後
  改成記憶體內傳遞，存檔時機怎麼定？
- ?from= 出生點分流的機制怎麼對應到 SPA 的參數？

**這項在 12 張新圖蓋完之前做效益最高（越晚搬越多）。但如果評估
工作量超過兩三天，也可以明確決定「這一作不做 SPA」，把黑屏
讀取畫面做漂亮（進度條＋一句世界觀文案）當替代方案——玩家
對「有內容的讀取畫面」的忍受度其實很高。**
