# 0. PRIMARY DIRECTIVE

Build a unified, scalable and visually convincing environmental response system for the Gensokyo RPG.

This system must connect:

1. A dynamic, spatially varying world wind field.
2. Height-dependent vegetation bending.
3. Wind-responsive architectural attachments.
4. Progressive movement of loose ground objects.
5. Wind-responsive river surface animation.
6. Water-current and wave-driven floating objects.
7. Reusable creature secondary motion for hair, clothing, tails, feathers and similar appendages.
8. Character locomotion inertia where appropriate.

These must not become disconnected animation systems with unrelated random values.

**One environmental field should produce coordinated but non-identical reactions across the world.**

The goal is natural movement, not perpetual synchronized oscillation.

The user specifically requires:

- Random-feeling but smoothly changing wind direction.
- Different wind strength at different positions.
- Different reactions for nearby objects.
- Stronger motion near the tips of tall trees.
- Slower motion in heavier or stiffer structures.
- Gradual acceleration, inertia and damping.
- Wind-responsive water surfaces and floating objects.
- A reusable creature solution rather than bespoke code for every NPC or monster.

Do not stop after creating architecture diagrams or API stubs.

Deliver a working runtime implementation with real integration evidence.

# 2. DEFINE THE SHARED SIMULATION CONTRACT

Implement or extend a central environmental wind service.

All subsystems must consume a consistent field definition.

## 2.1 Required public interface

Provide an interface equivalent to:

```gdscript
sample_wind(world_position: Vector3) -> Vector3
sample_wind_at(world_position: Vector3, time_sec: float) -> Vector3
sample_wind_strength(world_position: Vector3) -> float

set_wind_preset(preset_id: StringName) -> void
set_wind_target(direction: Vector3, strength: float) -> void
trigger_gust(...) -> void
set_wind_seed(seed: int) -> void
```

This is a conceptual contract, not mandatory copy-paste code.

Inspect actual Godot 4.7.2 APIs and choose an appropriate implementation.

Define clear units, coordinate conventions and parameter ranges.

Prefer wind velocity vectors in world space, with response models deriving approximate forces as needed.

Avoid treating an arbitrary animation amplitude as physical wind speed.

## 2.2 Deterministic simulation

Given identical:

- Seed.
- World position.
- Simulation time.
- Wind state.

The field must return the same result.

No frame-by-frame uncontrolled randomization.

Use deterministic procedural fields.

Simulation behavior must not depend on renderer frame rate.

Distinguish simulation time from visual rendering time.

Document pause, slow-motion, map-transition and save/load behavior.

## 2.3 Smooth directional variation

Wind direction must be able to evolve organically.

Requirements:

- Slowly drifting prevailing direction.
- Irregular gust duration.
- Calm periods.
- Gradual strengthening and weakening.
- Smooth directional changes.
- Occasional larger shifts without snapping.
- Bounded angular change rate.

Do not instantly assign a random direction each frame.

## 2.4 Spatial variation

Implement a multiscale wind field using smooth spatial and temporal variation.

Suggested layers:

- Large-scale prevailing wind.
- Propagating gust fronts.
- Medium-scale local variation.
- Small-scale turbulence.
- Height-dependent exposure.
- Optional authored shelter or exposure volumes.

Nearby samples should generally correlate, but must not be identical.

Allow local directions to differ from the prevailing direction without making the wind visually chaotic.

Use shared spatial coordinates rather than per-object independent oscillation.

## 2.5 CPU and GPU consistency

Vegetation shaders and gameplay-side objects must receive a consistent wind state.

Use suitable Godot 4.7.2 shader parameter mechanisms.

If CPU and GPU use approximations of the same field:

- Document the difference.
- Ensure gust timing and principal direction remain coherent.
- Establish a measured acceptable deviation.
- Avoid visible contradictions between adjacent shader-driven and physics-driven objects.

Do not update thousands of objects individually merely to feed identical global parameters.

# 3. VEGETATION MOTION SYSTEM

## 3.1 Height-weighted bending

Trees must not bend uniformly.

Introduce normalized structural height or authored vertex weighting.

An initial response profile may use:

```text
bend_weight = pow(normalized_height, exponent)
```

The exponent should be tunable by plant type.

Requirements:

- Root displacement approximately zero.
- Trunk movement increases gradually with height.
- Crown and branch tips respond more strongly.
- Tall trees may have greater absolute tip movement.
- Greater height must not automatically imply implausible deformation.
- Rotation and bending should preserve plausible structural continuity.

Use local mesh coordinates or explicit masks.

Do not assume every imported mesh uses the same pivot, orientation or scale.

## 3.2 Hierarchical movement

Where geometry supports it, separate:

1. Primary trunk or stem bending.
2. Secondary branch or crown response.
3. Fine foliage flutter.

These should have different response times and damping.

The trunk may begin returning before leaves stop moving.

Do not make the entire tree behave like one rigid swinging object.

## 3.3 Species response profiles

Create reusable vegetation profiles.

At minimum distinguish:

- Grass.
- Small shrubs.
- Bamboo.
- Broadleaf trees.
- Conifers where present.

Expose:

- Stiffness.
- Wind sensitivity.
- Height exponent.
- Maximum bend.
- Damping.
- Response delay.
- Branch/crown lag.
- Fine flutter amplitude.
- Turbulence response.

Apply stable per-instance variation.

Repeated trees should not move identically.

## 3.4 GPU scalability

Use GPU deformation for large vegetation populations where practical.

Avoid individual CPU animation for thousands of grass instances.

Check MultiMesh compatibility.

Validate:

- Pivot behavior.
- Culling bounds.
- Animated shadows.
- LOD transitions.
- Ground anchoring.
- Wind under nonuniform scaling.

Do not modify unrelated vegetation geometry to force a shader technique to work.

If an asset is unsuitable for convincing deformation, document or adapt it selectively.

# 4. ARCHITECTURAL ATTACHMENTS AND GROUND OBJECTS

## 4.1 Classification

Do not assume every visible object is movable.

Classify compatible environmental assets into:

**FLEXIBLE_ANCHORED**

Examples: curtains, flags, hanging cloth.

**RIGID_SUSPENDED**

Examples: lanterns, signs, wind chimes.

**LIGHT_LOOSE**

Examples: leaves, paper, dry fragments.

**MEDIUM_LOOSE**

Examples: unsecured baskets, small empty containers.

**STATIC_HEAVY**

Examples: stone lanterns, structural beams, fixed market equipment.

Unknown assets default to STATIC.

## 4.2 Physically informed response

Response must depend on more than mass.

Consider:

- Wind-relative surface orientation.
- Projected exposed area.
- Approximate aerodynamic drag.
- Mass and inertia.
- Anchoring.
- Static friction.
- Dynamic friction.
- Damping.
- Restoring torque.
- Local wind shelter.

A lightweight but narrow item should not necessarily move more than a broad item of equal mass.

Avoid arbitrary weight-only displacement multipliers.

## 4.3 Progressive motion

For loose objects:

1. Wind force builds.
2. Static resistance is overcome if sufficient force exists.
3. Velocity increases gradually.
4. Displacement accumulates over time.
5. Momentum persists briefly as wind decreases.
6. Friction gradually stops motion.

Never teleport an object when a wind-strength threshold is reached.

Never snap an object back to its authored position during visible gameplay.

## 4.4 Anchored objects

Hanging and flexible objects must retain their fixed attachment points.

Use appropriate methods:

- Shader deformation.
- Lightweight spring/pivot movement.
- Skeletal secondary motion.
- Limited physics simulation only when justified.

Maintain stable transforms and deterministic baseline behavior.

Do not move structural building collision bodies for cosmetic wind effects.

## 4.5 Safe asset integration

Do not automatically replace all village decorations with RigidBody3D instances.

Use opt-in registration or reusable receiver components.

Exclude:

- Quest-critical objects without explicit authorization.
- Navigation blockers.
- Protected architectural content.
- Sealed attachments that cannot safely be modified.
- Objects owned by concurrent sessions.

Moving loose objects must have well-defined reset and persistence policies.

# 5. RIVER SURFACE SIMULATION

The river must exhibit visibly dynamic motion beyond static water or simple texture scrolling.

Do not implement full fluid dynamics.

## 5.1 Separate water-flow and wind-wave components

The river requires two distinct influences.

### Water current

Represents sustained downstream flow.

It primarily determines:

- Floating-object advection.
- Directional foam and surface detail.
- General river motion.
- Local current variations.

### Wind

Represents moving air over the water surface.

It primarily determines:

- Small surface ripples.
- Wave amplitude modulation.
- Direction-dependent surface disturbance.
- Fine normal variation.
- Secondary influence on floating objects.

The wind direction must not simply replace the downstream current direction.

A river flowing east can still experience wind from the north.

## 5.2 Surface motion layers

Implement appropriate combinations of:

- Slow broad undulation.
- Directional ripples.
- Fine normal-map detail.
- Existing flow-map or UV movement.
- Localized bank and obstacle disturbance where supported.

Avoid uniformly repeating wave patterns.

Avoid excessive ocean-style waves in a shallow inland river.

Use appropriate river-specific scale and amplitude.

## 5.3 Wave-height sampling

If visible water geometry is displaced vertically, provide a compatible water-height sampling method for floating objects.

Expose a reusable interface conceptually equivalent to:

```gdscript
sample_water_height(world_position: Vector3) -> float
sample_water_normal(world_position: Vector3) -> Vector3
sample_water_flow(world_position: Vector3) -> Vector3
```

Use a clearly documented interface and coordinate system.

Floating objects must respond to the same wave representation used for the visible surface, within an explicitly tested approximation.

Do not animate visible waves independently while making floating objects bob with unrelated sine functions.

If V1 uses normal-only water motion without physical displacement, document this and use a consistent low-amplitude proxy for floating-object motion.

## 5.4 River integration safety

Inspect existing water mesh ownership, materials, collision, banks and bridge geometry.

Do not destroy existing water rendering to insert another competing shader.

Avoid:

- Shoreline gaps.
- Water clipping through banks.
- Floating dry patches.
- Unnatural wave motion beneath bridges.
- Transparency sorting regressions.
- Broken reflections or shadows.
- Excessive water vertex displacement.
- New Z-fighting.

Use the actual river scene as a validation target.

# 6. FLOATING OBJECTS AND BUOYANCY RESPONSE

Implement a reusable floating-object component.

## 6.1 Combined water and wind movement

Every supported floating object should combine:

- Local water height.
- Local water surface normal.
- Water current.
- Wind vector.
- Exposed area.
- Object mass.
- Drag.
- Buoyancy response.
- Rotational damping.
- Anchoring or tether constraints.

Use a lightweight physically informed approximation.

Do not attempt full hydrodynamics.

## 6.2 Different object behavior

Test at least two distinct classes.

### Light floating object

Examples: leaf or thin wooden fragment.

Expected behavior:

- Fast response to small ripples.
- Relatively strong yaw variation.
- Greater wind influence.
- Faster adaptation to local current changes.

### Heavier floating object

Examples: small barrel, log or floating container.

Expected behavior:

- Slower response.
- Greater inertia.
- Smaller angular acceleration.
- Smooth settling after disturbances.

### Anchored object

If a suitable example exists:

- Remains within tether constraints.
- Bobs and rotates without unlimited downstream drift.
- Does not teleport back to its anchor.

## 6.3 Stability requirements

No:

- Objects falling through the water.
- Unbounded rotation.
- Violent bobbing in gentle conditions.
- Teleportation.
- Uncontrolled drift into inaccessible map regions.
- Sudden snapping at scene transitions.
- Extreme collision jitter.

For temporary debris, define safe despawn or recycling rules.

For persistent interactive objects, define save/load requirements.

Do not globally activate physics on every decorative river asset.

# 7. UNIVERSAL CREATURE SECONDARY MOTION

This is a reusable animation feature, not a requirement to physically simulate every biological mesh.

## 7.1 Core principle

Creatures should optionally support wind-responsive appendages through a shared component.

Supported appendage categories:

- Hair.
- Tails.
- Fabric strips.
- Sleeves.
- Cloaks or haori sections.
- Feathers.
- Long flexible ornaments.
- Other suitable skeletal appendages.

The same component should work across different compatible rigs.

Do not assume every creature has identical bones.

## 7.2 Profile-based rig binding

Design reusable response profiles defining:

- Skeleton path.
- Bone-chain mapping.
- Root anchor.
- Chain length.
- Stiffness.
- Damping.
- Wind influence.
- Motion inertia.
- Maximum angular displacement.
- Collision or clipping limitations.
- LOD level.

Support naming conventions as optional discovery aids:

```text
hair_*
tail_*
cloth_*
sleeve_*
feather_*
```

However, bone names alone must not be considered sufficient proof of correct chain structure.

Validate hierarchy and bind poses before applying motion.

Unrecognized rigs must fail safely without breaking animation.

## 7.3 Motion inputs

Creature secondary motion must combine:

**Environmental forces**

- Local wind.
- Local gusts.
- Height-dependent wind.
- Directional turbulence.

**Creature movement**

- Linear velocity.
- Acceleration.
- Turning/angular velocity.
- Jumping.
- Landing.
- Relevant attack impulse, where safely available.

Example:

A character runs forward against a crosswind. Hair should respond to both air-relative motion and the character's own inertia.

Do not simply add a global sine wave to the skeleton.

## 7.4 Animation integration

Inspect the existing AnimationTree, Skeleton3D, animation modifiers, bone constraints and update order.

Choose a supported Godot 4.7.2 integration method.

Secondary motion must be applied at a controlled point after or in coordination with authored animation so that existing animation playback does not unpredictably overwrite it.

Requirements:

- Preserve existing animation poses.
- Preserve combat animation timing.
- Preserve bone hierarchy.
- Avoid accumulated transform drift.
- Avoid double-transforming the same bone.
- Reset or stabilize correctly after scene reloads and animation transitions.
- Remain stable at varying frame rates.

Do not globally modify animation import data or skeleton weights.

## 7.5 Simulation tiers

Provide three quality tiers.

### Tier 0: Disabled

No secondary simulation.

Suitable for distant or incompatible creatures.

### Tier 1: Lightweight

Short bone-chain response.

Suitable for ordinary nearby NPCs and monsters.

### Tier 2: Enhanced

Higher-quality spring response, more detailed inertia and optional clipping management.

Suitable for important characters.

The system should choose simulation detail based on relevance and distance.

Avoid high-frequency simulation for offscreen creatures.

## 7.6 Pilot ownership rule

Do not modify Yoriichi's real character files unless ownership is confirmed and there is no concurrent conflict.

If the character rig is currently owned by another session:

- Use a disposable compatible rig or test scene.
- Implement the reusable component independently.
- Demonstrate the API and animation interaction.
- Produce an exact integration handoff.
- Do not claim the production character is fully integrated.

Do not sacrifice ongoing Yoriichi combat or animation work to satisfy this mission.

# 8. SPATIAL COHERENCE ACROSS ALL SYSTEMS

The central acceptance requirement is that wind behaves like one shared natural phenomenon.

At the same world time:

- Grass samples the local wind.
- Tree crowns respond with delayed, height-weighted motion.
- Noren and flags flutter.
- Suspended lanterns swing with inertia.
- Loose leaves or paper accelerate gradually.
- Water ripples respond to local wind.
- Floating objects respond to current plus wind.
- Creature hair and appendages respond to wind plus locomotion.

These must not use unrelated randomized motion generators that contradict one another.

Wind direction and gust propagation should remain recognizable across object categories.

At the same time, no two object types should exhibit identical animation amplitude, frequency or response delay.

# 10. PERFORMANCE REQUIREMENTS

This is a large-world RPG.

The implementation must remain scalable.

## 10.1 Establish baselines

Measure before and after under comparable conditions:

- Village runtime.
- Beast Path runtime.
- River view.
- Vegetation-heavy view.
- Nearby active prop view.
- Nearby animated-character view.

Measure where supported:

- CPU frame time.
- GPU frame time.
- Physics frame time.
- Draw calls.
- Scene loading.
- Shader variant or compilation cost.
- Active simulated object count.

Use the same camera paths and quality settings.

Do not compare runs with different background workloads without acknowledging the limitation.

## 10.2 Optimization strategy

Prefer:

- GPU vegetation deformation.
- Shared shader parameters.
- Limited physics objects.
- Distance-based animation updates.
- Sleeping inactive objects.
- Bounded active simulation populations.
- Stable per-instance seeds.
- Reused materials and shaders.
- Predictable simulation time steps.

Avoid:

- Physics simulation for thousands of grass blades.
- Per-frame raycasts for every tree and decorative object.
- Per-frame mesh reconstruction.
- Duplicated wind-controller instances.
- Excessive shader permutations.
- Allocating large temporary arrays every frame.
- Updating faraway creature bone chains unnecessarily.

## 10.3 Performance gate

Set explicit performance budgets from the measured baseline before mass integration.

As an initial engineering target, aim to keep the added environment-system cost below approximately 1 ms of CPU frame time in representative heavy scenes, while separately measuring GPU impact and preserving the project's actual frame-time target.

This is a target, not permission to hide measurement failures or degrade existing rendering.

If representative performance regresses significantly:

1. Profile the affected subsystem.
2. Identify the dominant cost.
3. Apply a targeted optimization.
4. Re-measure.

Do not lower scene quality indiscriminately.
