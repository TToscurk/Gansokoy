# 幻想鄉 NPC Living World System — 自主生活與動態事件開發

## 一、開發目標

目前正在開發幻想鄉遊戲，使用 Godot 4.7.2。

請以《巫師 4》UE5 技術展示中的 Living World、NPC 自主行為、環境互動與連鎖事件為設計參考，擴充現有 NPC 互動系統。

**核心目標：讓所有已實裝的 HERO 擁有符合原作性格的生活行為，不再只是站在原地、隨機巡邏，或對著不存在的角色說話。**

NPC 應該像真正生活在幻想鄉的居民，即使玩家不與他們互動，也會自行安排活動。

本次開發以可見、可驗證的實際遊戲效果為優先，不要求複製 AAA 引擎技術，也不要求大型語言模型即時生成對話。

---

## 二、開發前先盤點現有系統

先以唯讀方式檢查專案，確認：

1. 所有 HERO 的實際清單、角色 ID、模型與場景來源。
2. 現有 NPC AI、巡邏、導航、任務與對話系統。
3. AnimationTree、動畫資產及互動動作。
4. 現有地圖、場景切換、導航網格及互動物件。
5. 目前是否已有事件排程器、時間系統或 NPC 狀態儲存機制。

不可自行假設角色、動畫、地圖或程式碼已存在。

先建立版本備份與可回復的開發基準。

接下來直接在本次授權的 NPC 互動系統範圍內實作，不需要停留在只有規劃文件的階段。

保留既有角色控制、戰鬥、場景和其他已正常運作的功能。

## 三、系統核心：NPC Autonomous Life Director

建立一套資料驅動的 NPC 自主生活事件架構。

每位 HERO 都需要具有：

- Character Identity：角色身分及原作背景
- Personality Profile：性格及行為偏好
- Relationships：與其他 HERO 的關係
- Daily Activities：常見生活行為
- Social Activities：可與其他角色共同執行的活動
- Environmental Interests：對環境物件的興趣
- Event Priorities：目前事件優先度
- Memory / Cooldown：近期執行的事件與冷卻資訊

事件可以使用權重隨機選擇，但必須受到角色身分、所在地點、時間、目標可用性及其他事件影響。

**禁止所有 HERO 共用毫無差異的隨機巡邏或對話流程。**

可共用底層動作，但每個角色的事件組合、觸發條件及表現方式必須不同。

## 四、HERO 自主生活事件

### A. 個人日常行為

角色依照自身特質主動執行事件。

範例：

魔理沙：
- 前往森林採集魔法蘑菇。
- 在市集尋找魔法材料。
- 研究收集到的物品。
- 遇到熟識人物時主動搭話。

慧音：
- 前往村莊巡視。
- 教學或整理教材。
- 與村民交談。
- 遇到異常狀況時主動調查。

靈夢：
- 打掃神社。
- 整理賽錢箱。
- 巡視神社周圍。
- 接待來訪的角色。

其他 HERO 必須依照原作背景、人物性格及實際可用場景建立相應行為。

不要將上述範例當成完整角色名單。

### B. HERO 之間的社交事件

允許 HERO 主動尋找其他 HERO。

例如：

魔理沙決定尋找慧音。

完整流程：

1. 確認慧音目前存在且可以互動。
2. 魔理沙選擇前往慧音的位置。
3. 使用現有導航系統移動。
4. 到達合理互動距離。
5. 雙方停止移動並面向彼此。
6. 播放適合的交談或待機動作。
7. 執行符合人物關係的對話或交流。
8. 雙方依照結果繼續原本的生活事件，或產生新事件。

**嚴格禁止：**
- 對不存在的 NPC 播放交談動作。
- 只有單方在對著空氣說話。
- 雙方距離過遠卻開始交談。
- 交談途中其中一人直接離開，另一人仍持續對話。
- 所有角色反覆播放同一套無意義台詞。

交談必須是一個由雙方共同參與、同步管理的事件。

如果對方正在戰鬥、忙碌或離開場景，必須能夠取消、等待或選擇其他活動。

### C. 環境物件互動

建立可重複使用的 Smart Object 機制。

互動物件可包含：

- 花草、蘑菇、藥草
- 市集攤位
- 座椅
- 書籍
- 桌面及工作區
- 神社清掃區
- 訓練區域
- 其他現有地圖物件

每個物件提供適合的互動位置、朝向、使用條件與動作需求。

例如：

魔理沙走到蘑菇前，蹲下採集，採集完成後起身，再前往下一個目的地。

這個事件不能只顯示「正在採集」的文字。

必須存在可見的移動、目標定位、執行動作和完成反應。

沒有適合動畫時，可以合理重用現有動畫或簡單的程序化動作，但不可把靜止不動偽裝成已完成。

如果缺少必要資產，必須明確列出缺口。

## 五、Dynamic Event Chain — 動態連鎖事件

這是本系統的重要部分。

NPC 事件不應永遠互不相關。

建立輕量化事件連鎖機制：

**事件 A 的結果，可以成為事件 B 的觸發條件。**

範例：

事件 1：
魔理沙前往市集。

事件 2：
魔理沙遇到慧音並開始聊天。

事件 3：
慧音提到森林出現異常。

事件 4：
魔理沙決定前往森林調查。

事件 5：
文注意到異常，主動前往採訪。

事件 6：
玩家在森林遇見正在調查的魔理沙。

上述屬於 NPC 自主世界事件，不必全部變成玩家任務。

支援：
- 預先設計的事件鏈。
- 根據角色狀態與環境觸發的事件。
- 玩家介入後改變事件結果。
- NPC 因其他 NPC 的行為改變目的地。
- 事件結束後恢復正常生活。

避免過度複雜的全域故事生成系統，優先實現可靠、可擴充、能實際觀察的事件鏈。

## 六、地圖載入後的行為

玩家載入地圖後，NPC 不應全部站在出生點等待指令。

應依照合理的初始狀態開始活動。

例如：

- 魔理沙準備前往市集。
- 慧音正在巡視村莊。
- 其他 HERO 正在採集、工作、交談或移動。

NPC 的活動可以錯開啟動，避免全體同時移動。

角色應從符合情境的位置開始活動。

避免玩家視線內突然生成、瞬移或不自然地切換動作。

如果專案具有時間系統，可讓事件受到早晨、白天、傍晚等時間影響。

如果沒有時間系統，不必為本功能額外重做整個遊戲時間架構。

## 七、事件執行狀態管理

每個事件至少具備：

- Available
- Reserved
- Traveling
- Interacting
- Completed
- Interrupted
- Failed
- Cooldown

所有互動目標都需要確認有效性。

多人互動事件必須預留參與者及互動位置，避免同一 NPC 同時參與兩個不同事件。

事件執行失敗時：

- 釋放所有預留資源。
- 結束雙方同步動作。
- 嘗試安全的替代事件。
- 必要時恢復合理的待機行為。

不可因為 NPC 導航失敗、目標消失或動畫未完成而永久卡住。

玩家主動交談、戰鬥或重要劇情事件，應能依優先權暫停或打斷一般生活事件。

## 八、角色個性差異

所有 HERO 的自主事件必須符合東方 Project 原作個性與人物關係。

不要把角色性格簡化成幾個隨機表情。

需要透過以下方式表現個性：

1. 選擇什麼活動。
2. 喜歡前往什麼地點。
3. 主動接近哪些人物。
4. 遇到其他 HERO 時如何反應。
5. 發生突發事件時會採取什麼行動。
6. 是否容易改變原定計畫。

例如：

魔理沙可能因發現稀有魔法材料而突然改變目的地。

慧音則更可能因村莊出現異常而放棄原本的工作。

角色行為的差異應該可以讓玩家透過觀察自然感受到。

## 九、所有 HERO 的實作覆蓋

本次開發不只針對魔理沙與慧音。

最終必須覆蓋專案中所有已實裝且可以作為世界 NPC 活動的 HERO。

每名 HERO 至少規劃三類有意義事件：

1. 符合人物背景的個人事件。
2. 合理的社交或環境互動事件。
3. 對玩家、其他 HERO 或環境變化的反應事件。

對於不適合主動社交的角色，可以用有性格特色的其他事件取代。

優先建立共用的移動、物件互動、社交及事件排程能力，再使用角色專屬事件資料覆蓋所有 HERO。

不要為每名 HERO 複製一套完整 AI 程式。

如果某名角色因資產、地圖或動畫限制而無法完成事件，必須在覆蓋報告中明確標示，不得聲稱已完成。

## 十、效能與場景管理

使用適合 Godot 4.7.2 的架構。

優先考慮：

- NavigationAgent3D 與既有導航系統整合。
- 利用現有 AnimationTree 或動畫控制器。
- Data-driven 事件定義。
- 事件優先權及冷卻控制。
- 互動物件預約機制。
- 遠距離 NPC 簡化模擬。
- 近距離 NPC 執行完整動畫與互動。

如果 NPC 遠離玩家，可降低更新頻率，並保留其邏輯活動狀態。

不可讓所有 NPC 每幀進行昂貴的目標搜尋或完整事件規劃。

避免大量角色同時爭搶同一個互動點。

## 十一、實作順序：優先產生可見成果

請採用以下順序，不要先花大量時間建立龐大的抽象系統。

### Phase 1：現況盤點與最小架構

確認目前所有 HERO、NPC 系統、動畫及地圖條件。

保留原本系統，實作最小必要的事件排程與同步機制。

### Phase 2：完成三個可觀察事件

優先使用已存在的角色和資產。

實作：

A. 單人環境事件：
HERO 主動移動、接近物件、執行動作、完成事件。

B. 雙人社交事件：
一名 HERO 主動尋找另一名 HERO，雙方在正確位置交談，結束後分開。

C. 連鎖事件：
第一個事件的結果讓另一名 HERO 改變活動計畫。

如果魔理沙與慧音都已存在並可於目前場景合理相遇，優先用兩人示範。

### Phase 3：擴展至所有 HERO

使用已驗證的底層行為系統，加入全部 HERO 的個性化事件。

盡可能重用共用動作。

不必為每位角色額外製作全套新動畫。

### Phase 4：實際遊戲驗證

必須使用 Godot 實際執行並驗證，不可以只看程式碼宣稱完成。

## 十二、驗收標準

請提供以下測試結果：

**測試 A：地圖載入**

載入後有 HERO 自動開始合理生活事件。

**測試 B：NPC 主動社交**

HERO 能主動找到另一個 HERO，並且真正完成雙人交流。

**測試 C：環境互動**

HERO 能找到物件、移動到互動點、執行動作、完成後離開。

**測試 D：事件鏈**

一個 NPC 事件能改變另一個 NPC 的行為或下一個目的地。

**測試 E：玩家介入**

玩家開始交談、接近事件或打斷活動時，NPC 不會卡死。

**測試 F：全部 HERO 覆蓋**

逐一驗證所有 HERO 至少有三類符合個性的事件設計，且可以在符合條件的測試場景觸發。

**測試 G：長時間運作**

使用加速事件測試或自動化測試，確認 NPC 不會因重複事件、目標失效或多人互動而卡死。

實際需要觀察的場景請提供錄影或畫面證據。

測試失敗不可跳過，也不可用文字敘述代替真實行為。

---

## 十三、開發限制

- 不要重做整個 NPC AI。
- 不要破壞目前已完成的角色、場景或戰鬥功能。
- 不要因缺少動畫就無限期卡在角色動畫修復。
- 不要使用假 NPC 或假對話充當系統完成。
- 不需要為了本次開發引入 LLM、外部 API 或大型 AI 框架。
- 不要為未來可能用到的功能建立過度龐大的架構。
- 不需要一次實作大量複雜劇情。
- 新功能要能持續增加 HERO、地圖、互動物件及事件資料。
- 必須優先產出玩家能直接看到的遊戲效果。

最重要的是：

**不要將「NPC 會走動」等同於「NPC 具有自主生活」。**

NPC 必須有目的地、執行原因、實際互動與行為結果。

## 十四、交付成果

完成後提供簡短報告：

1. 新增或修改了哪些系統。
2. 已覆蓋的 HERO 數量與名單。
3. 每名 HERO 已實裝的事件。
4. 已完成的社交事件與連鎖事件。
5. 實際遊戲測試與錄影。
6. 尚缺的動畫、互動物件或功能。

請先完成最小可玩的事件組合，再逐步擴充所有 HERO。

本次優先目標是：

**當玩家走進幻想鄉時，能看到角色正在過自己的生活，而不是所有 NPC 都在等待玩家觸發對話。**
