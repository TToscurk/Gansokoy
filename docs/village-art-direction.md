**狀態**：已定案（2026-08-04 的 grilling 問答）
**用法**：任何「這樣好不好看」的判斷**先查這份**。查不到就問使用者，**不要猜**。

## 0. 為什麼要有這份文件

v14~v18 五輪裡，返工的六件事——

| 返工項目 | 使用者的原話 |
|---|---|
| 草叢 | 「這個方塊的草到底是什麼」→「很像西瓜黏上去」 |
| 材質 | 「目前的素材很單調」 |
| 效能 | 「我電腦變卡了」 |
| 池塘 | 「池塘的石頭很醜」→「設計個有藝術性的池塘」 |
| 街道材質 | （參考圖四張全是夯土，我做成石板） |
| 建築高度 | 「場景和建築都很高很有幻想鄉的獨特味道」 |

——**全部是我自己猜的美術方向，而且全部猜錯**。每次都是先做完、被打回、
再重做。根因不是技術能力，是**沒有一份講死的規格**。

這份文件把「產生器裡每一個美術決定」攤開講死。**規格沒寫到的地方 = 要問，
不是要猜。**

## 1. 風格基準線

| 項目 | 決定 |
|---|---|
| **整體風格** | **偏卡通，混一點寫實** —— 不是純 PBR 寫實，也不是純低模 |
| **幻想鄉的「味道」** | **古代／近代／現代的混合體**（細節擱置，見 §5） |
| **樹** | 維持低模卡通，但要做好。v19 加了分枝與雙倍面數，使用者仍不滿意（「沒有更像樹的嗎」）——**下一輪在 Blender 認真重雕**，且訂為規矩：**有機造型一律 Blender 先做、preview.py 看過才進場景**（使用者原話：「模組先進 blender 做」） |
| **建築材質** | 保留程序化 PBR 貼圖，但**色彩往卡通拉** |

### 1.1 兩邊打架的問題

現在**建築是寫實 PBR、樹是低模卡通**，同一個畫面裡互相打架。
使用者選了偏卡通，所以統一方向是**往卡通靠**：

- 貼圖：降低髒污與噪點強度、提高飽和度
- 法線貼圖：減弱強度
- 全域輕微色階化／描邊後處理（待評估，不一定做）

### 1.2 參考作品的定位

使用者給過兩份參考，它們**不是同一種東西**，不要混為一談：

| 參考 | 是什麼 | 我們取它的什麼 |
|---|---|---|
| 《求聞編年史》 | 手繪 2D 俯視、色彩鮮豔、無光照 | **構圖與色彩濃度**（攤販、暖簾、招牌堆滿顏色） |
| 《幻走スカイドリフト》 | 3D、材質偏平 | **街的比例與立面**：窄街、二層連棟、真壁木框、紅燈籠橫過街道、街尾鳥居 |

兩份都**不是**要一比一複製的目標風格。目標是「偏卡通混一點寫實」。

## 2. 硬指標

| 項目 | 決定 |
|---|---|
| **效能取捨** | 畫面優先，但**效能三件套排在所有畫面工作之前** |
| **目標硬體** | 現在：Intel Xe 筆電／之後：**GTX 1070** |
| **色彩濃度** | **祭典等級** —— 燈籠串、旗幟、幔幕 |
| **朱紅（博麗色）** | 可以稍微加入 |
| **庭池** | **池泉庭園**（有水、曲岸、中島、石橋），不是枯山水 |
| **稻田** | **留著，但要重做**。⚠ v19 試過撒畦與水鏡失敗（田面起伏 >0.2m，水鏡變成 704 塊玻璃板，使用者要求拿掉）——正確做法要先把田整成**梯田式平整台地**（地形工程），才輪得到鋪水 |
| **幾何合併器** | 先不做 |
| **「做完」的定義** | **可玩的場景**：有 NPC、商店、可進的室內 |

### 2.1 效能三件套

⚠ **每一項加畫面的工作之前，這三項要先做完。** 不然只會愈加愈卡。

不動幾何、只改屬性：

1. **`visibility_range_end` 距離剔除**
   小裝飾件（柱／貫／窗框／格子／雜物／樽／俵）在 40~80m 外不畫。
   全村橫跨 500m，任一時刻畫面裡只有一小塊 —— 預估砍掉
   **60~70% 的有效 draw call**，而且玩家看不出來。
2. **小件關陰影**（`cast_shadow = OFF`）
   陰影 pass 等於把所有東西再畫一次。小於 1m 的裝飾件關掉等於再省一半。
3. **縮短 `directional_shadow_max_distance`**

**驗收要目視確認遠處沒有東西突兀地「消失」**——距離剔除最容易出這個問題。

### 2.2 draw call 基準

```bash
grep -c 'type="MeshInstance3D"' godot/maps/village/village.tscn
```

**基準：11,825**（v18）。正常的遊戲場景該在 2,000 以內。

⚠ 距離剔除**不會**讓這個數字下降 —— 它減少的是「同時被畫出來的數量」。
要靠實機目視與 Godot 的 Rendering monitor 判斷。

## 3. 尺度規則

### 3.1 內外一致（硬規則）

使用者原話：

> 「我站在建築物前面就能感受到裡面的大小與這個房子內部是一致的感覺」

因為「做完」的定義包含**可進室內**，這條從美感問題變成**可驗證的硬規則**：

- 室內以**京間 1.82m** 為模數排榻榻米與柱距
- 建築外部 footprint 必須裝得下室內配置（外 ≥ 內 + 牆厚）
- **要變成 `check_map.gd` 的一條自動檢查**：有室內的建築，
  外部 footprint 面積 ≥ 室內面積 × 1.15，否則報錯

### 3.2 地標尺度

| 建築 | 現在 | 目標 |
|---|---|---|
| **稗田邸主屋** | 17.5 × 11.5 × 高 4.0（基壇 19 × 13） | **≥ 25 × 15 × 高 6.5**，入母屋屋頂、二層 |
| 寺子屋 | 22 × 12 × 高 4.6（坐 1.5m 石垣） | 維持或再拉高一階 |
| 一般町家（町方） | 二層 5.4~6.6m | 維持 |

使用者明確點名的顧慮：

> 「要確保建築不會有算錯卡到其他東西的問題」

**放大會撞既有的地權系統。每次改尺度都要跑滿 `check_map.gd` + `walk_test.gd`。**

### 3.3 街道

維持現況：本通 8m／橫町 7m／巷道 4.5m。
**窄街才襯得出建築高**——放大地標後若比例失衡再回頭調，不要先動街寬。

## 7. 工序

排序依據：**先讓它不卡**（否則後面每一項都在惡化體驗）→ 再補畫面 →
最後才是可玩性。

| # | 工作 | 關鍵檔案 | 風險 |
|---|---|---|---|
| 1 | **效能三件套** | `gen_village.gd`、`scripts/main.gd` | 低；要目視確認遠處沒東西消失 |
| 2 | 地標放大（稗田邸為主）＋ 內外一致檢查進體檢 | `gen_village.gd:1539`、`tools/check_map.gd` | **中**：會撞地權 |
| 3 | 樹重做 | `assets/blender/make_trees.py` | 低；先用 `preview.py` 看模型 |
| 4 | 庭池改池泉庭園（曲岸／中島／石橋） | `gen_village.gd` 庭池段、`gen_lib.gd` 的 `pond_carve(wobble)` | 中 |
| 5 | 祭典級色彩（燈籠串、旗幟、幔幕）＋ 一點朱紅 | `gen_village.gd` | 低；**會加 draw call，必須在 1 之後** |
| 6 | 遠景地理（妖怪之山／竹林／神社山） | `gen_village.gd:240`、新竹子 glb | 低 |
| 7 | 稻田重做（畦／水／田埂道） | `gen_village.gd` 田野段 | 低 |
| 8 | 室內 4~5 間 + NPC + 商店 | 新場景 + `scripts/` | **高**：這是新系統不是美術工作 |

## 8. 每一項的收工條件（不變，ADR-016）

```bash
godot --headless --path godot --script tools/gen_village.gd
godot --headless --path godot --script tools/check_map.gd -- village    # 要 0 問題
godot --headless --path godot --script tools/walk_test.gd -- village    # 要 0 條不通
xvfb-run -a godot --path godot --rendering-driver opengl3 -- \
  --map=village --shots=res://tools/shots/village_key.json --shotdir=/tmp/x
```

- 五張快檢照**逐張看過**（完整的 28 張要 ~25 分鐘，收工前才跑）
- **新資產先跑單模型預覽**，不要為了看一個模型重算整張村子：
  ```bash
  blender -b -P godot/assets/blender/preview.py -- <name>
  ```
