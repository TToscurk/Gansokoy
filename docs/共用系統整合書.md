# 《緣一・幻想鄉》共用系統整合書 —— GameCore 統一執行層
> 基於 main（81aac4e）分析。目標：每張地圖只寫「這張圖獨有的東西」，
> 其餘全部由共用層提供。與 /buildloop 分開跑，這是一次結構性重構。

---

## 1. 現況診斷

模組化其實已經做得不錯——`src/` 底下該切的都切了（environment、
daycycle、weather、hud、controller、progression、quality、optimize…）。
**問題不在模組，在「組裝」**：每張圖都要自己把這 17–20 個模組
重新接一次線。

實測數據：
- 每張圖 17–20 行 import，其中 15 行以上完全相同
- 每張圖各有 11 處樣板呼叫（renderer 設定、camera、Environment、
  HUD、Controller、Progression、quality、resize、animate）
- renderer 那段初始化 9 行，六張圖一字不差

**後果**（你已經感受到的）：
1. 神社有時刻顯示，其他圖沒有——不是刻意設計，是主場景先做的東西
   沒同步到後來的圖。這類「功能孤島」會隨圖數增加而擴散。
2. 神社有完整後製鏈（GTAO/Bloom/SMAA），其他圖只有基本 renderer——
   同一款遊戲兩種畫質標準。
3. 之後每加一個新系統（存檔、音效、成就、地圖 UI），
   要開 18 個檔案各接一次；漏一張就是一個孤島。
4. 蓋新圖的心智負擔：600 行的圖，前 120 行是抄來的樣板。

## 2. 目標架構

```
src/core/GameCore.js          ← 新：統一執行層（唯一組裝點）
  ├─ 渲染層   renderer / camera / composer（後製鏈分級）
  ├─ 世界層   Environment（天氣時刻）/ quality / fog
  ├─ 玩家層   角色模型 / Controller / Progression / vitals / loadout
  ├─ UI 層    HUD / ESC / 對話 / 任務誌 / 時刻顯示 / 地圖UI（未來）
  ├─ 系統層   combat / mobcore / hazard / portal / 存檔 / 音效（未來）
  └─ 迴圈層   單一 animate()，各子系統註冊 update 回呼

maps/<id>/<id>.js             ← 只剩「這張圖獨有的東西」
  export const meta = { id, playSize, fog, spawn… }
  export function buildWorld(ctx) { …地形、建築、裝飾、怪、NPC… }
```

**每張圖的檔案應該長這樣**（目標）：
```js
import { GameCore } from '../../src/core/GameCore.js';

const core = await GameCore.boot({
  mapId: 'sunflower',
  postFX: 'full',          // 'full' | 'basic'，取代目前神社獨有的後製鏈
});

const { scene, world, ctx } = core;
// —— 以下才是這張圖真正獨有的內容 ——
// 地形、建築、裝飾、怪物、NPC、傳送點…

core.registerUpdate((dt, t) => { /* 這張圖獨有的每幀邏輯 */ });
core.start();
```
樣板從 120 行降到 5 行。

## 3. 分階段實作（重點：不要一次改 18 張圖）

### 階段 A：建立 GameCore，先只讓一張圖用
1. 新增 `src/core/GameCore.js`，把 sunflower.js（最新最乾淨的一張）
   的樣板整段抽出來，做成 `GameCore.boot()`。
2. 提供的東西：renderer/camera/scene/world、Environment、quality、
   玩家（模型＋Controller＋Progression＋loadout）、HUD＋ESC、
   resize 處理、單一 animate 迴圈與 `registerUpdate()`。
3. sunflower.js 改用它，**行為必須完全不變**——跑 /playtest sunflower
   對照重構前後，任何差異都是 bug。
4. 這階段不要碰其他圖。

### 階段 B：後製鏈分級，消除畫質雙標
1. 把 main.js 的 GTAO/Bloom/SMAA/ShaderPass/OutputPass 後製鏈
   移進 GameCore，做成 `postFX: 'full' | 'basic' | 'off'`。
2. 與 quality.js 的三檔連動：高＝full、中＝basic、低＝off。
   （目前神社獨有 full，其他圖全 basic，是歷史遺留不是設計。）
3. sunflower 先切 full 看效能與觀感，截圖 A/B 給我決定
   其他圖要不要跟進。

### 階段 C：功能孤島盤點與統一
把「只有某些圖有」的功能全部收進 GameCore，讓所有圖一致：

| 功能 | 現況 | 目標 |
|---|---|---|
| 右上角時刻顯示 | 只有神社 | 全圖（HUD 標配） |
| 地名顯示 | 部分 | 全圖，讀 mapRegistry 的名稱 |
| 後製鏈 | 只有神社 | 依 postFX 分級 |
| ZoneTracker 地帶追蹤 | 只有神社 | 有子地帶的圖都能用 |
| 對話 Dialogue | 有 NPC 的圖各自接 | GameCore 統一，有 NPC 就自動有 |
| 任務誌 QuestLog | 只有神社 | 全圖 |
| SceneEditor | 各圖各自 import | GameCore 統一（dev 環境才載入） |
| debug handle | 部分 | 統一 `window.debug`，給 /playtest 用 |

**做法**：先產出一份盤點表（Grep 每張圖的 import 差異），
列出「哪張圖缺哪個功能」，再逐項收進 GameCore。

### 階段 D：其餘五張圖遷移
一次一張，每張遷移後跑 /playtest 對照，確認行為不變才進下一張。
順序：eientei → namelessHill → bamboo → trail → village → main.js（神社最後，
它最複雜、獨有東西最多）。

### 階段 E：為未來預留的擴充點
GameCore 建立這幾個「插槽」，之後加新系統只改一個檔案：

```js
GameCore.use(SaveSystem);     // 存檔（目前散在 localStorage）
GameCore.use(AudioSystem);    // 音效／BGM（還沒有，遲早要）
GameCore.use(MinimapSystem);  // 地圖UI（品質升級書的升級 5）
GameCore.use(VistaSystem);    // 遠景延伸（品質升級書的升級 1）
```
每個系統實作統一介面：`{ init(core), update(dt,t), dispose() }`。
**品質升級書的升級 1（遠景）與升級 5（地圖UI）建議等 GameCore
做完再實作**——否則又要在 18 張圖各接一次線。

## 4. 存檔與跨圖狀態（順手解決）

目前跨圖靠 localStorage 手動存取，散在各處。GameCore 統一收攏：

```js
core.state          // 記憶體內的當前狀態（HP/MP/等級/任務進度/已探索地圖）
core.save()         // 寫入 localStorage（換圖前自動呼叫）
core.load()         // boot 時自動呼叫
```
Schema 集中在一個檔案，加新欄位不用翻 18 張圖找 localStorage 呼叫。
**注意**：如果之後真的做 SPA（效能清單任務 5），這層會變成純記憶體
傳遞，介面不用改——所以現在先做這層是划算的。

---

## 5. 風險與守則

- **這是重構，不是加功能**：每個階段的成功標準是「行為完全不變」，
  不是「看起來更好」。任何觀感差異都要查清楚是不是 bug。
- **每階段獨立 commit**，出事好回退。
- **不要同時跑 /buildloop 蓋新圖**——會產生沒吃到 GameCore 的新孤島。
  重構期間暫停蓋圖，或蓋完 kourindou 再開始重構。
- 神社（main.js）最後遷移：它有最多獨有邏輯（後製鏈、ZoneTracker、
  任務系統），前面五張圖跑順了再處理它。
