## 2. PHASE 1 做了什麼

新檔 `godot/assets/blender/make_machiya.py`，產 `machiya_f_a`。
`make_town.py` 的模組迴圈對 `PROTO = {"machiya_f_a"}` 改呼叫它 ——
**manifest 仍由 `make_town.py` 統一寫出**（一份 manifest 一個寫入者，
兩邊各寫一份遲早對不上）。

### 真壁造：軸組先立，漆喰填進去

```
土台 150×150 → 柱 150×150（四角通し柱 + 正背面管柱 + 側面管柱）
            → 貫 105×30（兩道，兩面各凸 30mm）
            → 内法長押 130×30
            → 桁 180×180（頂面齊屋面起點）
```

漆喰是**逐格嵌板**、比柱面**內縮 25mm**。那 25mm 的落差就是真壁造在遠景
唯一讀得出來的東西 —— 牆不再是一個連續量體，柱是真的比牆凸出來，
陰影線是**幾何**不是貼圖。

### 立面（四開間，刻意不對稱）

```
bay0 出格子（凸 0.34m 的盒子：底板＋持ち送り＋兩側板＋障子背板＋直櫺＋上枠）
bay1 連子格子（腰板＋障子＋直櫺＋上下框）
bay2 大戶口（兩片板戶＋橫桟＋敷居）＋ 庇
bay3 連子格子
```

### 庇：完整構件

腕木 → 前桁 → 垂木（看得到的椽）→ 野地（含厚度）→ 鼻隠し → 軒裏（仰視面，
木色不是瓦色）→ 丸瓦。出簷 0.95m、坡度 17°。

### 屋頂：一組構件

野地（厚 0.16）→ 鼻隠し → 軒裏 → 垂木（出簷段，18 根）→ 丸瓦（本瓦葺きの
縱向半圓，每側 26 條）→ 軒瓦（簷端巴瓦）→ 妻壁（**漆喰**）→ 破風板 →
懸魚 → 棟（熨斗瓦 + 冠瓦）。

## 3. 三個在製作中實際炸出來、修掉的問題

1. **總高 4.78 ≠ 規格 4.50。**
   舊版的棟只有一根 0.14 的方條，新版是熨斗＋冠瓦兩層 0.26。屋身反推公式
   扣的還是 0.14，差的 0.28 全部往上長。天際線的階梯是使用者定案過的，
   prototype 不許順手改掉 → **屋身讓棟**，內法高同時收到 1.72。

2. **桁戳穿屋面。**
   第一版把桁擺成「坐在 z_wall 上往上長」，而屋面在牆線的高度就是 z_wall
   —— 桁往上凸 0.18 直接穿出屋頂，正是規格明列的禁項
   `roof intersecting wall`。改成**桁頂面齊 z_wall**。
   同一個理由拿掉了小屋梁：它架在兩道桁之間、擺在那個高度一定穿出屋面，
   而平入切妻的妻側看到的是妻壁與破風板，梁端本來就被遮住。

3. **Godot 的 glTF 匯入快取不會自己更新。**
   換成六材質的 glb 之後，`semantic_mesh()` 讀回來仍然是 **1 個 surface**
   —— 讀到的是 `.godot/imported/` 裡舊的 `.scn`。要先
   `rm .godot/imported/machiya_f_a.glb-*` 再 `godot --headless --import`。
   **這條要寫進流程**：模組的材質結構改變時，光重跑 Blender 不夠。

## 4. 材質身分怎麼活著走完管線

```
Blender 六個材質（WOOD / WOOD_LT / PLASTER / STONE / KAWARA / SHOJI）
  → glTF 匯出：一材質一 primitive（實測 Primitives created: 6）
  → Godot 匯入：Mesh 6 surfaces，材質名帶著
  → gen_lib.semantic_mesh()：逐 surface 依**名字前綴**換成專案的 pbr() 材質
  → MultiMesh
```

`gen_town._emit_batches()` 的判斷依據是 **surface 數 > 1**，不是寫死模組名
—— Phase 2 加新模組時不用再改那裡。legacy 的四個單 surface 模組自動走舊路徑。

⚠ 名字比對要**長名優先**（`WOOD_LT` 不能被 `WOOD` 吃掉）。對不上的名字
保留 glb 自己的材質、不亂猜。

## 6. Known visual risks（人工審核時請特別看這幾點）

1. **屋身只有 2.29m。** 4.50 的總高扣掉 23° 屋頂（1.655）與棟（0.26）之後就
   剩這麼多。真壁造的立面節奏（腰→貫→內法→小壁）被壓得很扁，小壁只有
   0.32m。要更好的比例只有兩條路：放寬總高規格，或收屋頂坡度 —— 兩者都會
   動到使用者定案過的天際線，所以 Phase 1 沒動。
2. **丸瓦（本瓦葺き）是強烈的選擇。** 它比桟瓦貴氣、也更「寺社」。如果人間
   之里的一般町家應該是**桟瓦**（民家的常見形），這一輪要改的是屋面那 52 條
   半圓 —— 改起來很快，但要先定案。
3. **出格子只做在 bay0。** 四開間裡只有一格凸出去，正面因此不對稱。這是刻意
   的（町家的店・住・通り庭各佔各的開間），但如果要更整齊的商業立面，
   應該是 bay0+bay1 都出格子。
4. **貼圖比例還沒調。** 語意材質直接接上專案既有的貼圖組（plaster / planks /
   dark_wood / roof_kawara / stone_wall / shoji），uv1_scale 沿用材質庫的預設值
   —— 那組數字是配 blockout 的大面積調的，貼到 0.15m 寬的柱子上會太密或太疏。
   Phase 7（Materials/Polish）的事，但近景審圖看得到。
5. **169 棟裡有多少變成新版**：`machiya_f_a` 這個 kind 的每一棟都換了。
   其餘四種仍是 legacy blockout，所以街上現在是**新舊混排**。這是驗證
   「新模組進得了現有管線」的必要條件，不是最終狀態。

## 8. PHASE 1.1 —— 比例與屋頂語彙重平衡

**觸發**：Phase 1 的 technical pipeline 批准，Art Review 未批准。
指令範圍：只改 `machiya_f_a`，不進 Phase 2，不改 village layout，
不改其他四個 legacy machiya。

### 8.1 為什麼 4.50 救不回來

4.50 扣掉 23° 屋頂（1.655）與棟（0.26）之後屋身只剩 **2.29m**，
屋頂佔立面 **42%**。那不是造型問題是**預算問題** —— 屋身沒有高度可以長出
真壁造的節奏（腰→貫→内法→小壁），細節怎麼調都救不回來。

### 8.2 5.40 的分配

```
基礎 0.30 ┃ 屋身 3.36 ┃ 屋頂 1.50 ┃ 棟 0.24        總高實測 5.42
屋頂佔比 42% → 28%
```

多出來的 1.07m 屋身**不是拉高一層樓**，是長出 **厨子二階（つし二階）**：
江戸～明治町家的標準形，一階內法之上一條矮夾層，開**虫籠窓**。
不這樣做的話，3.36m 高的牆上半段會是一片空白漆喰 —— 屋頂不壓迫了，
換成牆壓迫。

坡度只收 2°（23° → 21°，約 3.8 寸勾配）。屋頂量體主要是被總高救回來的，
不是靠壓坡度 —— 規格明講「不要把町家變成低坡現代住宅」。

### 8.3 立面新增的兩件

| 構件 | 為什麼 |
|---|---|
| **虫籠窓（塗り込め）** | 它不是格子：木骨外面裹一層漆喰，所以櫺條又厚又圓、顏色跟牆一樣。剪影上是一排粗胖的白豎條，跟一階那排細而深色的連子格子形成對比 —— 這個對比就是町家立面的招牌 |
| **通し庇（橫貫整個面寬）** | 這是把「屋頂壓倒立面」真正解掉的那一件。3.36m 高的立面需要一條水平線切成「一階店面／厨子二階」兩段，否則屋頂縮小了牆還是一整片。原本只罩住入口的庇改成參數化元件，跑一次全寬 |

内法高從 1.72 放回 **1.85**（一般町家的常見值，5.40 的總高終於養得起它）。

### 8.4 本瓦葺き → 桟瓦葺き

使用者定案：一般 `machiya_f_a` 用樸素的桟瓦，本瓦葺（深半圓的丸瓦）留給
未來的富戶／寺社／地標。兩者在幾何上的差別就是實作上的差別：

```
本瓦：深半圓丸瓦壓在平瓦接縫上（凸 52mm）—— 剪影是一排粗肋
桟瓦：一體成型的波形瓦，只有淺桟（凸 22mm），而且**橫向的葺き足
      （每列的重疊段差）才是主節奏**
```

所以改成：**淺桟（定尺 305mm 間距）+ 橫向列線（葺き足）**。
⚠ 葺き足做成**貼在坡面上的細條**，不切開坡面本身 —— 切開的話坡面會變成
一階一階的樓梯，30mm 的段差在 5m 外根本看不出是瓦、只看得出是鋸齒。
軒先也跟著換：桟瓦的軒先瓦是**連續的唇**，不是本瓦那排圓形巴瓦。

## 9. PHASE 1.5 —— Human Village Vertical Slice

**目的**：停止雕單棟，用 9 棟建築的一段街回答「整體畫面能不能脫離
procedural demo」。**不是**整村重做 —— 169 棟、六座地標、河流、稗田邸
一律沒碰。

### 9.1 為什麼是獨立場景

新 map `maps/slice/`（`tools/gen_slice.gd`，46m 見方）。
village 的佈局是 `_block()` 的 169 筆 frontage 明表，改一格就要重跑全圖 +
五道閘門，一輪 6 分鐘；slice 一輪 **25 秒**。審圖要能**反覆**才有意義。

### 9.2 街道構圖：planned irregularity，不是 random scatter

**沒有一個 `randf()` 決定建築的位置、朝向或退縮。**全部寫在 `LOTS` 明表，
每一筆帶 `why` 欄位。亂數只出現在「同一種雜草的角度」這種層級。

| 手法 | 實作 |
|---|---|
| frontage setback | 退縮 3.0~3.9m，鄰棟之間差 0.4~0.7m（店面搶街是商業街的常態） |
| yaw variation | ±0.03 rad（約 1.7°）。大到看得出不是尺規排的，小到相鄰簷口不打架。真實町並みの不整齊就是這個量級 —— 歪的是**地界**不是房子 |
| alley gap | 北側 x=−3.7 一條 2.64m 的巷 |

## 11. PHASE 1.7 —— Material readability pass

### 11.1 四項問題與各自的修法

| # | 症狀 | 真正的成因 | 改了什麼 |
|---|---|---|---|
| 1 | 漆喰讀成**斜向瓦楞板** | `uv1_scale = 0.40` → tile 2.5m。一面 3.6m 的牆只吃到貼圖的 1.4 個週期，貼圖裡的方向性被放大成整面牆的圖案 | uv `0.40 → 1.55`（tile 0.65m）、`normal_scale 0.65 → 0.14`、albedo 提亮加暖 |
| 2 | 夯土讀成**粗砂礫場** | 兩層疊加：地形 shader 的 `dirt_tile` 太粗 **＋ 每棟 26 顆、20–40cm 的「牆腳碎石」灑到街上** | `dirt_tile 2.6 → 5.4`、`path_tile 4.2 → 2.2`、`dirt_tint` 壓暗加暖；碎石半徑 5.4→5.05（收回牆腳）、尺寸 0.10–0.20→0.06–0.11、每棟 26→15 顆、專用暗土色材質 |
| 3 | 木紋比例 | WOOD tile 0.31m ≈ 兩倍柱寬，方向沿柱長 —— **這一項檢查後判定是對的，沒改**。WOOD_LT（腰板）稍碎，`1.6 → 1.35` | 只動 WOOD_LT |
| 4 | 桟瓦在遠景**摩爾紋** | 幾何（31 條桟 × 葺き足）在遠景全部保留 ＋ 高對比亮藍白瓦 ＋ 掠射角的各向同性 mipmap | `lod_bias = 0.5`（提早降級）、`TEXTURE_FILTER_..._ANISOTROPIC`、KAWARA albedo `(0.80,0.86,1.00) → (0.60,0.63,0.68)`、`normal 0.35 → 0.18`、桟改成**連續波浪**（半寬 0.030→0.118、葺き足 0.265→0.46m） |

### 11.2 漆喰的三段調校（值得記著）

一開始把 uv 從 0.40 直接推到 2.40（tile 0.42m），方向性的確消失了 ——
但變成砂紙／混凝土骨材的高頻雜點，一樣不像抹面。最後停在 1.55：

```
0.40（tile 2.50m）→ 一面牆 1.4 個週期 → 斜向瓦楞板
2.40（tile 0.42m）→ 一面牆 8.6 個週期 → 砂紙
1.55（tile 0.65m）→ 一面牆 5.5 個週期 → 抹面 ✓
```

「細緻」跟「低頻」是互相拉扯的兩個要求，中間那一段才是漆喰。

### 11.3 白石的真兇不是地形貼圖

先調 `dirt_tile` 之後畫面**更糟**：土路變暗，原本混在亮土裡的白石反而
一顆顆跳出來。實際去讀 `_build_ground()` 才發現 `MM_牆腳碎石` 的半徑 5.4
已經越過 4.9 的正面線——石頭根本不在牆腳，是灑在街上的。
`rock_mat_dry()` 的 albedo 又是 1.14 的亮白。

> ⚠ 沒有動 `rock_mat_dry()` 本身：village 的河石在用它。slice 改用自己的
> `slice_pebble` 材質。同理石溝／路邊石／踏石也只在 slice 內壓暗。

### 11.4 桟瓦：從「細條」改成「連續波浪」

原本是在一片平屋頂上長 31 條半寬 0.030 的細條 —— 條與條之間是平的，
遠景取樣就是黑白黑白的高頻。改成半寬 0.118 的連續波浪之後，同樣是
31 個週期，但**沒有平地**，降級成低解析度時會平均成一片灰而不是雜訊。
面數反而少了：2962 → 2834（KAWARA 1038 → 910）。

葺き足從 0.265m 放到 0.46m 是**可讀性換真實性**的取捨，寫在這裡不藏：
真桟瓦的葺き足約 0.24–0.28m，現在的值接近兩倍。

## 12. PHASE 2 —— Architecture Kit（六戸の町家）

Phase 1.7 の Art Review が通り、残っていた最大の指摘は §10.3 に書いた三項：
**天際線が平ら・面寬が全部同じ・立面が逐格同じ**。materials をこれ以上
いじっても解けない —— モジュールが一種類しかないのが原因だから。

### 12.1 variation の設計原則 ——「同一文化、不同家庭」

指示された一行が設計の全部を決めた：**「不要追求每棟都不同，而是建立
『同一文化、不同家庭』的感覺」**。実装ではこう分けた。

| | 内容 | 理由 |
|---|---|---|
| **不変**（人の尺度） | 内法高 1.85・柱 150・貫 105・長押 130・腰板 0.62・犬走り・材質 6 種・真壁の填め方・桟瓦の葺き方 | 一条の街で門の高さが家ごとに違うことはない。**内法線が揃っている**ことが「同じ文化」の一番強い信号 —— 材質より強い |
| **可変**（家の尺度） | 間口 5.2~9.8・総高 4.85~6.40・厨子二階（無／虫籠窓／真二階）・開間構成・平入/妻入・庇の長さと位置・卯建・煙出し・勾配 19~23° | 間口＝地価と家業の規模、厨子の高さ＝建造年代と財力、卯建＝金持ち、煙出し＝火を使う職種。全部**社会的事実**に対応させた |

配分も意図的に偏らせてある：**f_a×3・f_o×2・f_n×2・f_s/t_a/w_a 各 1**。
一戸ずつ全部違うと町並みではなく**見本市**になる。標準形が何軒かあって、
その間に金持ち・職人・新築・仕舞屋が挟まる比率のほうが「集落」に見える。

### 12.3 「偽の variation」を避けるために実際にやったこと

規格の禁止事項は「同一 mesh に scale／rotation をかけただけ」。
一番あやしいのは**妻入り**（回せば作れてしまう）なので、そこだけ書く。

`machiya_t_a` は f_a を 90° 回したものでは**ない**。回っているのは
**屋根の生成座標系だけ**で、軸組・立面・庇・腰板は街向きのまま生成される。
技術的な核は高さ予算の一行：

```python
span = W if tsuma else D          # 屋根が落ちる方向の全長
body = total_h - plinth - (span/2)*tan(pitch) - RIDGE_STACK
```

平入りは**進深**が、妻入りは**面寬**が屋根の rise を決める。だから同じ
総高でも屋身の高さが変わり、立面の割り付けそのものが変わる。回転では
絶対に出ない差。

実装は `MB.xf`（頂点変換）。⚠ **行列式が正の回転**でなければならない：

```python
bld.xf = lambda p: (D_r*0.5 - p[1], p[0] + W_r*0.5, p[2])   # det = +1
```

鏡像（det = −1）にすると繞序が全部裏返り、Blender では両面描画なので
気づけず、Godot で背面剔除されて屋根が丸ごと消える。docs §3 の
「参道が丸ごと消えた」のと同じ罠を、同じ理由で二度は踏まないための注記。

### 12.4 このラウンドで壊して直したもの

1. **pitch の二重変換。** `build_variant()` は degrees を取るのに、Phase 1
   の呼び方をそのまま移植して radians を渡していた。21° が 0.37° になり、
   屋根がほぼ平らに。**気づけた唯一の兆候は f_a の面数が 2834 → 2858 に
   変わったこと** —— 総高は反推なので合ってしまうし、絵も「低い屋根の家」
   に見えるだけで破綻はしない。既知の正解と数字を突き合わせる価値。
2. **無かった穴を塞いで本物の穴を開けた。** 妻側の出は下から見たら裏面が
   見えるはずだと思い込んで、破風面と**同一平面**に軒裏の三角形を追加
   → z-fighting で妻面が真っ黒。lineup の一枚目で即バレて撤回。
   実際には破風の三角形が端を塞いでいて穴などなかった。
3. **軒が食い込んでいた。** 隣棟間隔を W（面寬）で測っていたが、f_a は
   W7.6 でも**屋根は 9.56** ある。0.5m 重なっていたのを俯視で発見 →
   manifest の `fw`（出簷込み）基準に直した。
4. **lineup のカメラが計算どおりに写らない。** 70mm/78m → 切れる、
   50mm/110m → まだ切れる。撮った絵から px/m を実測して 145m に。
   画角は理屈で決めて、**絵で検算**する。

### 12.5 地面の処理が三年ぶんまとめて間違っていた（Phase 1.5 からの累積）

Phase 2 で footprint がバラバラになった拍子に露見した。`_lot_center()` が
返すのは**正面の面**であって量體の中心ではない（docstring にそう書いてある）
のに、使う側が全部「中心」のつもりで使っていた：

- **門前の敷石**：`fz = c.y − side*4.9` は建物の**中**（土間の真ん中）。

  ほうを撫でていただけで、原因はこれ。今は壁 footprint に沿った楕円。

手置き値のままだと、仕舞屋の荷物が隣の家の前に置かれる）。

## 13. PHASE 2.5 —— 店先と暮らしの構図（三軒の hero building）

Phase 2 で建築は「同じ家に見えない」ようになった。残った「きれいな
建築模型」感の出どころは**店先が空だったこと** —— どの家の前にも同じ
汎用の荷物が同じ角度で置いてあった。ここは三軒だけ、一軒ずつ業を決める。

### 13.1 構図の原則：散らすのではなく、業を語る

## 15. PHASE 2.6b —— 布のクリアランス修正（審図の差し戻し）

Phase 2.6 の審図：**不承認**。布が建物と交差していた。

### 15.1 何が起きていたか

近景で撮って確認した二件（`d2`/`d3`）：

- **酒屋の暖簾**：庇の**前桁が上帯を貫いていた**。暖簾の天が 2.08m 固定、
  前桁は先端で 1.99〜2.12m —— ちょうど重なる高さだった。
- **紺屋の染め布**：1.88m の反物を庇と主屋根のあいだに吊っていたが、
  そこは約 1.09m しかない。**庇を突き抜けていた**。
- ほか、提灯の吊り紐（0.30m）も庇の上に突き出ていた。

原因は共通で単純：**配置側が屋根面の高さを知らなかった**。`beam_z 2.08` も
`dy 1.18` も目分量で、庇の勾配とも主屋根の軒裏とも無関係な数字だった。

### 15.2 直し方 —— 数字を計算に変える

1. **manifest に面を出す**（`make_machiya.build_variant`）：
   `hisashi{z, proj, slope, thick, beam_back}`・`eave{z_wall, overhang, pitch, thick}`。
2. **gen_slice に天井関数**：`_hisashi_bottom(m, dz)` / `_hisashi_top(m, dz)` /
   `_roof_soffit(m, dz)` / `_hang_dz(m, dz)`（前桁より内側へ丸める） /
   `_hang_y(m, dz, up, drop, upper)`。
3. **吊り物の表から絶対高さを消した**。書くのは「どの天井の下か（`upper`）」
   「上下にどれだけ伸びるか（`up`/`drop`）」「そこからさらに下げる量（`dy`）」だけ。
   汎用の店（hero 以外の七軒）も同じ関数を通る。
4. 入らないものは**寸法のほうを直した**：染め布 1.88→1.26m（庇の下に吊る）、
   簾 1.04→0.78m（庇と軒裏のあいだに収める）、提灯の紐 0.30→0.16m。

### 15.3 `cloth_strip` のクリアランス規則（再利用可能）

```python
cloth_strip(..., clear_front=None, clear_side=None, thick=0.012)
```

- `clear_front`：前方の最大振れ `sway+bow+ripple+thick` がこれを超えるとき、
  **三つをまとめて同じ率で**縮める。形の比率は保ち、量だけ落とす。
- `clear_side`：裾の横ずれ `|tilt|·w` を頭打ちにする（隣の布と当たらない）。
- 縮小率には下限 `CLOTH_FLOOR = 0.28`。**ゼロにはしない** —— 平らな布は
  布ではない。ここまで詰まる場所は変形ではなく配置が間違っているので、
  規則はあえて「まだ当たる」ままにして、配置のバグを隠さない。

⚠ 正直に書いておく：**今回の交差を実際に解いたのは §15.2 の配置修正で、
クリアランス規則ではない**。現在の値では規則はほぼ非拘束（暖簾 k≈0.99、
染め布 k≈0.98、簾・物干し k=1.0）。これはガードレールであって、
今回の修理そのものではない。拘束が効くのは「布の正面 20cm 以内に物を
置いた」ときで、そのとき初めて自動で縮む。
