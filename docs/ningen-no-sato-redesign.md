# 人間之里 街區重設計 Feature List

**來源**：使用者 2026-08-05 的開工規格（含空拍幻想鄉參考影片修正）。
**狀態標記**：✅ 已做｜🔨 本輪動工｜⏳ 排隊中｜🚫 明確排除

## 範圍
本階段只做**街道／街區重設計（地圖幾何）**。明確排除：
- 🚫 戰鬥／衝刺用的碰撞牆準備（明確延後）
- 🚫 農田系統（獨立階段，未開工）
- 🚫 人群／NPC 模擬（等 NPC 系統存在）

## 1. 複合街區（Compound Block）
| 項目 | 規格 | 狀態 |
|---|---|---|
| 打破格線 | 每街區 3~4 棟町家，交錯排成 **L 形或ㄇ形** | 🔨 |
| 前後錯位 | 棟與棟之間前後錯 **1~2m**，拆掉僵硬的矩形院牆 | 🔨 |

## 2. 階梯天際線（修訂版 —— 更戲劇化）
| 項目 | 規格 | 狀態 |
|---|---|---|
| 前排 | **4.5~5.5m** | 🔨 |
| 後排 | **9~10m**（接近翻倍，不是原本溫和的 2.5m 差） | 🔨 |
| 村緣 | 極端縮小至 **3.5m** | 🔨 |
| 後排屋頂 | **45° 斜度**，給街道視角壓迫感 | 🔨 |
| 驗證方式 | **必須在引擎內街道視角驗證**，不能只看俯瞰 blockout | 🔨 |

## 3. 12m 主橋
| 項目 | 規格 | 狀態 |
|---|---|---|
| 形制 | 日式**半拱木橋**，寬度對齊 12m 主路 | 🔨 |
| 拱高 | 頂點 **+1.5m** | 🔨 |
| 欄杆 | **1.1~1.2m** | 🔨 |
| 親柱 | 隨橋寬等比放大，站在橋上要讀得出份量 | 🔨 |
| 鏤空欄杆 | 上下橫木之間留空，配合**確認過的日照方位**投影 | 🔨 |
| 過橋不對稱 | 過橋後**左高壓／右低開**，刻意不對稱 | 🔨 |

## 4. 水系優先的規劃邏輯（重大修正）
看過空拍幻想鄉參考影片後確立：**水路是城鎮的結構脊椎，不是撒在格線上的裝飾**。
| 項目 | 規格 | 狀態 |
|---|---|---|
| 先定河道 | 先畫蜿蜒河道，複合街區**順著水的曲線**排，不是先畫格線 | 🔨 |
| 小橋 | 路網自然需要過水的地方補 **1~2 座小橋** | ⏳ |

## 5. 街道生活密度層（**後續疊加，本輪不做**）
| 項目 | 規格 | 狀態 |
|---|---|---|
| 地面雜物 | 商品溢到街上、疊起的籃／桶 | ⏳ |
| 簷下吊掛點 | 布旗、燈籠、招牌 —— 密度依商業／住宅氛圍變化 | ⏳ |
| 地標建物 | 每個大街區一座（水車、鐘樓），打破町家的均質 | ⏳ |
| 背景層次 | 遠景屋頂剪影 + 山，給出街區以外的尺度感 | ⏳ |
| 花樹密度 | 同種花樹**大群聚**做色塊衝擊，不是散點單株（稗田邸教訓） | ⏳ |

## 6. 建置策略（已定案）
| 決策 | 內容 |
|---|---|
| **參數化產生器優先** | 先寫町家街區產生器（參數：街區尺寸、高度梯度、對水角度），再談手擺 |
| **第一步就 MultiMesh** | 不重蹈稗田邸「單一 mesh blockout、事後轉換」的錯 |
| **Blender 只做模組** | 町家變體、橋、吊掛道具各自輸出獨立 `.glb`，**不在 Blender 組整條街** |
| **佈局邏輯在 Godot** | 資料驅動的產生器腳本（讀模組庫 + 參數，MultiMesh 批次實例），沿用 `gen_village.gd`／`gen_kourindou.gd` 模式 |
| **絕不先合併建築群再匯入** | 合併就毀掉 MultiMesh 的意義 |
| 多代理平行 | 更大規模時考慮（等共用模組庫驗證過） |

## 本輪交付順序（使用者指定）
1. Blender/Godot 分工先確立（模組 vs 佈局）
2. **町家街區參數化產生器** —— 真正的第一交付物，不是渲染圖
3. **河道路徑** —— 定義／確認蜿蜒河道穿過城區的走法（佈局跟水走，先有水才能擺街區）
4. 1~3 就位後：用產生器生出第一個複合街區（**寬橋核心區**），出預覽給使用者驗收
   —— 跟稗田邸一樣的節奏：先做一件、驗收、再批量。

### ⚠ 先更正我上一輪講錯的一件事
第一輪我說「正對面平視時後排只勉強探出前排屋脊，幾何上剛好卡在臨界」——
**那是用 (脊高−眼高)/距離 粗估的，錯了**。屋脊在進深方向有位置、屋頂還有
出簷，斜率估算兩者都沒算。

這輪改成**射線 × 實際三角形**（`scratchpad/sightline.py`：從匯出的 glb 取
真的三角形，從馬路對面眼高 1.7m 射向後排屋脊做 Möller–Trumbore）：

| | 遮擋仰角 | 後排脊仰角 | 露出帶 |
|---|---|---|---|
| 前排 4.8/5.4（第一輪） | 11.08° | 13.04~14.67° | 1.2~2.2 m |
| 前排 4.5（本輪） | **8.57°** | 13.04~14.95° | **2.69~3.57 m** |

也就是說：第一輪其實**沒有**卡在臨界，後排本來就露得出來（+1.95~3.59°）。
壓到 4.5 是把露出帶**加倍**，決策方向仍然是對的，但我當初給的理由是錯的。

## 第六輪：樹的結構回歸 + 兩份產生器合併（2026-08-06）

使用者指出：sato 的櫻花是「圓柱樹幹 + 疊 2~3 顆壓扁的球」，完全沒有枝條
結構 —— 而這正是稗田邸的楓**花了八版修掉**的那個問題。

### 病根（比視覺問題重要）
專案裡有**兩份互不相干的樹產生器**：

| | 檔案 | 供應 | 骨架 |
|---|---|---|---|
| A | `make_hieda.py`（私有實作） | 稗田邸的楓／松 | 遞迴分枝，改了八版 |
| B | `make_trees.py` | **village / trail / kourindou / sato 全部** | 棒棒糖 |

A 的八版修正**從來沒有回流到 B**。所以每開一張新圖、每加一種新樹，
棒棒糖就再生一次 —— 人間之里的櫻與背景綠樹就是這樣長出來的。
只修 sato 的櫻花會讓同一個回歸在下一張圖再發生。

### 修法：抽出 `tree_lib.py`，兩邊共用
純 Python（不 import bpy），呼叫端提供一個 builder（`tri`/`quad`/`tri2`/`use`）。
搬過去的是**已驗證的那份**：遞迴分枝 `grow`、枝端葉團 `canopy_from_tips`、
松的葉盤 `canopy_pads`、短寬葉 `leaf_tuft`，連八版累積的註解一起搬
（「不放暗色團塊 → 像鳥巢」「半徑取 u^0.45 不是均勻取樣」…）。
`make_hieda.py` 的私有實作全部刪掉改成別名，`make_trees.py` 重寫成
「品種參數 → 灌 mesh → 匯出」。

**合併安全性驗證**：稗田邸四棵樹重新產生後 tri 數 3024/3144/3144/7226
**與合併前完全相同**，glb 連 git 都沒列為 modified（位元組相同）——
RNG 呼叫順序沒被動到，已定案的樹一根枝都沒變。

### 新的散佈樹（骨架同源，參數不同）
稗田邸是 8~11m 的庭木特寫（3,000 面／棵、單株擺放）；這些是幾百上千棵的
MultiMesh 散佈，所以 `depth` 少一層、`ntuft` 砍到 1/4~1/2。**骨架不能省**：
棒棒糖的病因在骨架，砍葉量不會讓它變回棒棒糖。

從匯出的 glb 實測（不是看參數）：

| 樹 | 葉子離軸心中位 | 葉子在 1m 外 | 樹皮露在葉外 |
|---|---|---|---|
| tree_round_a | 1.24m | 63% | 22% |
| tree_round_b（vista） | 1.09m | 54% | 26% |
| tree_sakura_a | 1.24m | 70% | 13% |
| tree_pine_a | 1.34m | 75% | 15% |

「葉子散在離軸心 1m 外」= 樹冠長在**枝端**不是疊在幹頂；
「樹皮露在葉外」= 裸枝打破實心剪影（規格第 3 點）。

### 兩條材質路徑都沒被動到（規格第 4 點）
每個 glb 一定要有**兩個 surface**：0=bark、1=foliage（材質槽的加入順序
就是匯出後的 surface 順序，從 glb 實測確認）。場景資源實測：

| 資源 | s0 | s1 |
|---|---|---|
| `mm_tree_round_a.res` | 有貼圖 單面 | **有貼圖** 單面（森林貼圖 × 頂點色，原路徑） |
| `mm_tree_sakura_a.res` | 有貼圖 單面 | **無貼圖 雙面**（密度層那輪修的花冠路徑，原封不動） |

合成單一 surface 的話兩邊都會把整棵樹當樹冠 → 花樹被森林貼圖乘成濁褐。

### 面數（sato 全圖樹木）
**1.03M → 1.05M 三角形（+2%）**。闊葉樹變貴，但竹子的葉團從 icosphere
換成葉片後從 1232/1584 掉到 718/898，剛好抵掉 —— 竹是最後一處球狀樹冠。

### 這輪的坑
1. **葉子大小是絕對公尺**：`leaf=0.50` 是為 8~11m 的庭木調的，同一個值放到
   4.6m 的散佈樹上相對大了 2.5 倍 —— 渲染出來是一叢尖銳碎片。新品種一律
   用 `leaf_h`（樹高比例）；`leaf` 只留給稗田邸那三棵已定案的樹。
2. **覆蓋率算不過來**：稗田邸的樹是 ~5× 葉片重疊才顯得密。散佈樹撐不起
   那個葉數，改成「葉片大一點、數量少一點」讓葉子彼此重疊成團。
   第一版直接照搬 ntuft 比例 → 樹冠像撒了一把彩紙。
3. **花色在引擎裡比 Blender 深一階**：sato 的 Environment 有 saturation 1.24，
   飽和的玫瑰色會被再推一階讀成洋紅。**引擎內截圖才是準的**，花色調淡後
   才是櫻。順帶記一筆：`d4` 那個機位是**逆光**（太陽在 +z 側），花看起來
   暗是光照的事實不是顏色錯 —— 另開 `d6-sakura-lit` 順光機位對照。

### ⚠ 其他圖還沒吃到這個修正
`village` / `trail` / `kourindou` 的 `.tscn` 在產生時就把 mesh **烤進**
`gen/*.res` 了，所以它們現在仍是舊的棒棒糖樹，直到各自重新產生為止。
沒有一起重跑是刻意的：village 馬上要被 sato 取代（整合輪），現在重烘
只會製造一份即將作廢的大 diff。**修正本身已經在共用產生器裡**，
那三張圖任何一次重新產生都會自動吃到。

## 草層 MIGRATE + 整合 Stage 3（2026-08-06）

### 草層：不是照抄，是重寫
舊圖六組草，新圖搬五組。**`rice_rows`（3,600 株）刻意不搬** —— 它走
`_field_w()` 農田權重，而農田是規格裡「🚫 獨立階段，未開工」的項目，
第二輪還為了它把遮罩 G 通道清零過。照抄等於把已明確延後的系統偷渡回來。

三處改寫（不是參數微調，是邏輯換掉）：
1. **避開鋪面改問 `mask_at()`** —— 那是地形著色器吃的同一份遮罩，
   草與地面貼圖因此永遠一致，不會「貼圖是石板、上面卻長草」。
2. **蘆葦改成沿河道取樣**。水際帶只佔全圖 1.7%，拒絕取樣 800 叢要撞
   48,000 次還撞不滿（實測只拿到 740/800，卡在 tries 上限）。
   沿線取樣 ~100% 命中且分佈均勻。
3. **密度梯度改看「離路緣多遠」而不是「離廣場多遠」**。舊圖的
   `r < CORE ? 10% : 60%` 硬半徑照抄到新圖後，整座城鎮都是光禿的綠地 ——
   因為 CORE=196 幾乎涵蓋全鎮（最外圈町家在 r≈189），玩家在鎮上走的
   每一格都吃那個 10%。改成路邊被踩禿、屋與屋之間長得起來、出村茂盛。

數量從 5,740 提到 **23,893 叢**：舊圖 2,600 叢長草攤在 600×600 上是
**每 57m² 一叢**，引擎內根本看不出有草層。tuft_mesh 一叢只有 5~9 個三角形，
2.4 萬叢也才 ~17 萬面，比樹便宜。

### ⚠ 這輪最大的坑：MultiMesh 的 visibility_range 是**整批**的
草做完之後畫面上**一根草都沒有**，但所有證據都說它在：節點在、
`instance_count` 對、mesh 與 ShaderMaterial 都在、位置驗證四項全過
（不在屋內／不在路上／不在河裡／蘆葦都在水際帶）。

真因：`visibility_range_end` 的距離是拿**整個 MultiMeshInstance 的 AABB**
算的，不是逐實例。草鋪滿整張 600×600 的圖，AABB 中心在地圖原點；相機站在
(−30, 230) 時離中心 232m > 設定的 120m → **整層草一次全部消失**。

診斷過程（記下來因為它示範了「別猜、去量」）：
先驗位置 → 全過；再驗是否被地形埋掉（地形是 221 取樣的線性內插面，
草的 y 用 `height_at` 精確算）→ 只有 14% 略低、最深 0.098m，不足以遮住
0.4m 的草；再試 `FADE_SELF → FADE_DISABLED` → **仍然沒有**；
最後從 9m 高垂直俯瞰一個「明明有 49 叢」的格子、一根都看不到 ——
才鎖定是整批被剔除。香霖堂的草沒事，因為那張圖只有 140×140。

**同一個 bug 也潛伏在密度層道具上**（`visibility_range_end = 110`）：
玩家走到村緣時整層暖簾／提灯／雜物會一次消失，之前沒發現是因為截圖
機位都在鎮中心。一併拿掉。

### Stage 3：mapRegistry 重烤覆寫
`tools/export-godot.mjs` 以前是把 JS 端的 registry 整包 `writeFileSync`
蓋掉 —— 只存在於 Godot 端的條目每次重烤就**靜靜消失**，沒有任何訊息。
改成**合併 + 大聲警告**：JSON 有、JS 沒有的條目一律保留並印出來，
要嘛去 JS 補上、要嘛確認退場後手動刪。主要真相來源仍是 JS，
但重烤不准靜靜刪東西。（已用單元測試驗過合併邏輯。）

### 驗收
草層位置四項檢查全 0、check_map 0 問題、walk_test 12 條全通、
引擎內截圖確認草真的畫得出來（村緣茂盛、街上踩禿）。

## 街緣設施＋水邊 MIGRATE（門樓／石溝／街燈／動物／水生植物，2026-08-06）

舊 `gen_village` 的 `_build_gates` / `_build_floor_decor`（石溝）/ `_build_lamps`
/ `_build_fauna` / `_build_water_plants`。**座標一個都不能照抄** —— 舊值全綁在
舊格線（街燈吃 ST_X/ST_Z、石溝寫死本通 x=±6.2、北門寫死 z=−215）與**已被移除的
水路**上。搬的是做法與比例，位置一律從新路網／新河道重新推。

### 亂數隔離
新增 `_street_rng`（`SEED + 5231`），材質全部指定色調索引 —— 只要碰一次
`_lm_rng.randf()`，六座地標的庭園散佈就整組換位置。**驗證方式不是宣稱而是實測**：
搬完之後把六座地標的子樹跟搬之前逐節點比對，位移 > 0 的節點數 **0 / 0 / 0 / 0 / 0 / 0**。

### 門樓（2 座）
北門擺在 trail 落點 (0,−174) 內側 6m —— 一落地就是**穿門進村**。西南門壓在
kourindou 引道（z=92，沿 x 走）上，所以轉 90°；舊圖那條引道是斜的。
補了一根「貫」：舊版只有樑與簷，剪影是「兩根柱撐一片板」。
門洞登記成保留區（在鋪街區**之前**跑），町家 169 棟不變。

### 石溝（103 節 → 3 個 MultiMesh）
舊版一節一個 Node3D 帶 3~4 個 box，光本通就 500+ 個節點。收成溝壁／溝底／溝蓋
三個 MultiMesh，橫街穿過來的 18 節改成整節石蓋（用**縮放**拉長，不是排 4 塊
1.6m 的板 —— 那樣重疊處會共面閃爍）。範圍吃商業梯度（`_commerce ≥ 0.45`），
石溝是町方的東西，村緣的排水是土溝。

⚠ 第一版用 `MAT_TONES["stone"]`，俯視截圖是**純白的軌條** —— 那組色調最暗的
一支也有 0.82，乘上本來就亮的 stone_wall 貼圖就是白的。跟護岸「0.42 的灰讀成
水泥防洪牆」同一個病。改成自建的 0.60 中灰之後才讀得出是排水溝。

### 街燈（21 盞）
改成**沿路網折線行走取樣**，間距吃商業梯度（村心 17m、村緣 48m），避開町家 OBB、
保留區與河道。OmniLight3D **不是 MeshInstance3D，`_perf_pass` 掃不到** ——
自己設 `distance_fade`（55m 起、15m 淡出）。

### 水邊生物（9 鴨 / 14 鯉 / 5 鷺鷥）
- 水面高度只有一個真相來源：`river_water(..., RIVER_DEPTH * 0.20, bank_h)`
  → 水面 = bank_h − 0.5。舊碼寫的是 `sink * 0.35`（水路的係數），照抄會整批浮高 0.375m。
- `fauna.gd` 的 speed 是**每秒走完全長的比例**不是 m/s。舊值 0.006~0.016 是配
  390m 水路寫的，搬到河上鴨子會用 3.7~9.9 m/s 巡游（比人跑快）。改成從真實速度回推。
- **鷺鷥第一版 600 次嘗試一隻都站不住**：舊版「沿法線外推岸 + 1m」在梯形斷面的
  水路上成立，在這條河上不成立 —— `river_carve` 的坡拖到 15.4m，「岸 + 1m」的
  地面還在水面下 0.9m。改成**往外走到地面剛好露出水面的那一格**，實測水際線在
  離河心 9.58m（河半寬 7.0、水面半寬 6.02）。

### 水生植物（睡蓮 220 / 荷 80）
蘆葦已經在草層（`_reed_along_river`），這裡只補睡蓮與荷。生長帶從舊版的
0~0.72 半寬（＝撒到河心）收到 **0.42~0.86**：浮葉植物長在淺灘不長在流心。
另外用 `poly_dist` 複驗每一株 —— 沿線法線外推在河道轉彎的內側會被推到對岸。

### 撿到的既有 bug：`tuft_mesh` 沒有預設材質
`tuft_mesh` 把顏色烤在**頂點色**上，但 `commit()` 出來的 ArrayMesh 沒有材質，
Godot 給預設白 —— 頂點色根本沒人讀。症狀是睡蓮／菖蒲／荷在引擎裡是一叢一叢的
**白色碎片**。草層之所以正常，是因為它每次都自己補 `grass_wind_mat`。
修在**單一收口**：`tuft_mesh` 自己掛一個預設材質，呼叫端照樣可以覆蓋。
影響面實測：`trail.tscn` 重跑後**位元組完全相同**（它三處都自己補了材質），
只有村圖那四處（水邊兩處＋稗田邸庭池兩處）從白色變回綠色。

### check_map 補上「生物錯位」
這支的檔頭從第一版就寫著要驗生物錯位，但**一直沒有實作**——
而那正是舊圖出過的 bug（九隻鴨疊在世界原點＝本通正中央）。現在驗：
鴨浮在水面 ±0.35m、鯉在水下 0.05~1.2m、鷺鷥不能泡在水裡。
實測 28 隻：鴨 −0.00~0.02、鯉 −0.38~−0.32、鷺鷥 +0.02~+0.05，全數通過。

### 誠實清單（本輪量到但沒有動的）
- **水面畫得比真正的水際線窄**：實測水面網格半寬 6.02m，而地形要到離河心
  ~9.6m 才露出水面 —— 中間 ~3.5m 是「低於水面但沒有水」的濕灘。村心那段被
  砌石護岸擋住看不到，村外那段坡很緩，讀成濕沙灘。要修得動 `RIVER_HALF * 0.86`，
  那會連帶影響護岸、橋、鵜呑亭川床與 check_map 的水面檢查 —— 不是 MIGRATE
  這一輪該做的事，記在這裡。
- 睡蓮用 `tuft_mesh` 做，形狀是**放射狀的葉叢**不是平貼水面的浮葉。這是舊
  builder 的做法，照原樣搬入。

## 稗田邸院內植栽（2026-08-06）

### 為什麼不是「把 maps/hieda/gen/*.res 搬過來」
實測三個數字：

| | 尺寸 |
|---|---|
| `hieda_garden.instances.json` 植栽擺位 | **95.4 × 107.0 m**（136 實例 / 10 種模組） |
| `hieda_blockout.glb` 本體 | **75.6 × 110.5 m** |
| 村圖稗田邸保留區 | **42.4 × 45.6 m** |

線性差 ~2.3×。而且村院塀內 38×41m 扣掉主屋／緣側／長廊／離れ／庭池之後，
真正能種東西的只有 **593 ㎡（38%）** —— 面積差 ~17×。整套塞進來只會是一叢
互相穿模的樹牆。那批資產是照**獨立地圖**做的（markers 裡還有一個 target 待填的
木戶 portal，blockout 也還沒有地形／碰撞／meta／mapRegistry 條目）。

使用者定案：**村院另做小型植栽**，重用同樣那 10 種模組、照村院的實際空地重排；
後院全套原封不動留給它自己那張圖。`gen_hieda.gd` 的檔頭已經把這三個數字與
「`maps/hieda/gen/*.res` 是刻意保留的孤兒」寫進去，免得下一個人以為壞了就刪。

1. **lm_ghost 的保留區檢查對 MultiMesh 全盲**：它只掃 `MeshInstance3D`，

2. **check_map 的散佈物檢查拿群組的合併 AABB 去比**：群組外框就是「整座宅邸」

### 回歸抓到的東西（不是走個形式）
**石溝的溝蓋浮在石板路上。** 本通街景截圖裡是一片「掉在路上的板子」，還帶影子。
原因：舊做法把一節溝錨在 footprint 的**最低點**（那是為了「斜坡上不要翹起來」），
但那只治了一半 —— 溝壁是沉的、埋掉沒人看得見；**溝蓋是浮的**（+0.04），
6m 長一片壓在 0.2m 落差上，遠端就架空 0.2m。
修法：節長 6m → **3m**，而且每一節錨在**自己中心**的 `height_at`。
順帶把溝蓋色調 0.70 → 0.56（在砂色石板路上還是太亮）。

這一項四道閘門**全部沒抓到** —— 它不是幾何錯誤（沒穿模、沒離地判定門檻）、
不影響可走性、也不在保留區問題裡。引擎內截圖仍然是唯一抓得到「看起來不對」
的閘門，這一輪再次驗證了那條規矩。
