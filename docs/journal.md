### ① 向日葵田：鏡頭吃進花叢

**只動 `maps/sunflower/sunflower.js`**，沒有碰鏡頭距離，也沒有碰其他地圖或共用層。

先量了鏡頭實際跑到哪裡（玩家站田埂中線、camYaw 轉一圈取最遠的方位）：

```
(-30, 10)   相機離路緣 2.55m
(23.6, 5.4) 相機離路緣 2.56m
(44, -60)   相機離路緣 2.61m
```

也就是說**玩家站在路中央時鏡頭根本進不到花區**（花是路緣外 3.2m 才種）。
會吃到花的是另外兩種情況：玩家走到埂緣，以及玩家直接踏進田裡 ——
花田沒有任何東西擋人，走進去鏡頭就整個沒入 1.9~2.9m 高的花海。

照搬竹林 block-clump 的兩半：

1. **近路疏、遠路密**：`density = min(1, (pd - 3.2) / RAMP)`，斜坡 `RAMP = 8.0` 公尺
   （竹林是 14 公尺；花田攤太長會把「一整片密不透風的黃」稀釋掉，所以縮短）。
2. **只有花叢才擋人**：`pd > 9` 且 0.6% 機率長成一叢（3~6 株），整叢給一個
   `post(x, z, 0.95, 地面+2.6)`。每一株都給碰撞盒會像卡在竹籤堆裡 —— 竹林踩過這個坑。

量化結果（相機周圍 1.8m 打 24 條立體射線，數幾條打到東西；每點轉四個方位取最糟）：

| | 田埂上・最糟 | 田埂上・平均 | 最近的花 | 田中央（對照組） |
|---|---|---|---|---|
| 修改前 | 4 / 24 | 0.75 | 0.74m | 平均 7.6 |
| 修改後 | 1 / 24 | 0.04 | 1.57m | 平均 8.5 |

花的總數 45458 → 43718（少 3.8%），花叢擋人處 253 個。

A/B 截圖：`shots2/sunflower-cam-before.png` / `-after.png`（同一個位置、同一個
camYaw）。before 那張正是你講的症狀 —— 整個畫面被花盤糊住；after 田埂清出來了，
花牆退到讀得出距離的地方。

**踩過一個坑，寫下來免得再走一次**：我第一版不是照抄竹林，而是自作聰明改成
「近路種矮株，讓鏡頭從花梢上掠過」。水平射線探針量出來全 0，看起來很成功，
但截圖一看畫面下緣兩坨巨大的黃盤子 —— 花盤從「相機上方」掉到「相機下方」而已。
**花盤太大，高矮這條路走不通，疏密才是對的**；探針也因此改成三層仰角的立體射線，
不然量不到相機腳下的東西。

**留給你判斷**：`RAMP = 8.0` 是唯一的視覺取捨旋鈕。覺得埂邊太空就調小（6 左右），
覺得鏡頭還是會擦到花就調大（10~12，往竹林的 14 靠）。改一個數字，不會動到別的。

### ② postFX 天空色：判讀結果（**沒有動代碼**）

#### 結論：參數是共用的，路徑不是

**共用的部分**（兩條 pipeline 完全一致，這一層沒有分岔）：

- `renderer.toneMapping = ACESFilmicToneMapping`（實測兩邊都是 enum 4）
- `renderer.toneMappingExposure` —— 由 `Environment.applyTime()` 每次重算，
  實測 full 圖與 basic 圖在同一時刻完全相同（正午 1.000、黃昏 1.100、深夜 1.293）
- 天空色的來源：`daycycle.js` 的 `sky[]` 色表 → `Environment.skyUniforms`，
  同一份 shader、同一份 uniform，兩邊共用

**不共用的部分（＝色差的來源）**：天空球是一顆**裸 `ShaderMaterial`**，
它的 fragment shader 只有 `gl_FragColor = vec4(c,1.0);`，沒有
`#include <tonemapping_fragment>`，也沒有 `#include <colorspace_fragment>`。
three.js 只會把這兩段注入內建材質，裸 ShaderMaterial 一律照你寫的輸出。於是：

- **basic**：直接畫上畫布 → 天空**既沒被 tone map、也沒被 linear→sRGB 編碼**
- **full**：畫進 EffectComposer 的 HalfFloat（線性）target → 最後 `OutputPass`
  把 ACES tone mapping ＋ sRGB 編碼**一起補上**

實測（同一時刻、同一天氣、鏡頭朝天頂，讀畫面像素）：

| 正午 12.5 天頂 | 色值 |
|---|---|
| 色表裡寫的 | `#0d47a8` |
| basic（人間之里、無名之丘，兩張完全一致） | `#011064` |
| full 但關掉 bloom / grade | `#003db2` |
| full 全開（太陽花田現況） | `#002fa5` |

`#011064` 不是隨機的：它**正好等於 `#0d47a8` 的 sRGB→linear 解碼值**
（0.051→0.0040、0.278→0.0630、0.659→0.3915，×255 = 1、16、100，三個通道全中）。
原因是 `new THREE.Color('#0d47a8')` 會把 hex 從 sRGB 轉進 linear 工作空間，
而 basic 那條路沒有人把它編碼回去 —— **basic 圖的天空一直比色表寫的更暗更濃**，
這不是設計，是漏了一段。

`gradePass` 只佔一小部分（`#003db2` → `#002fa5`）；**主要的差距是 tone mapping
與色彩空間那一段，不是分級**。所以「把 grade 關掉就一致了」是行不通的。

#### 建議（等你點頭再動手）

**方案 A（建議）**：修天空 shader，把 three.js 那兩個 chunk 補回去，
讓裸 ShaderMaterial 跟內建材質走同一套輸出規則。
- 好處：**一行顏色值都不用改**，兩條 pipeline 自動對齊；而且畫進 render target 時
  three.js 會把 toneMapping 設成 None，chunk 自動變 no-op —— 同一份程式碼在
  full 與 basic 兩條路徑上都正確，這正是內建材質的行為。
- 代價：**basic 五張圖的天空會整體變亮一階**（正午天頂從 `#011064` 變成
  `#003db2` 那個口徑）。神社一直是 full，所以色表八成本來就是照 full 調的 ——
  修完應該是「回到你原本想要的樣子」，但這句需要你的眼睛確認。
- 動到的是共用層（`src/world/environment.js`），一次影響八張圖。

**方案 B**：不修 shader，把全部地圖切成 `postFX: 'full'`（整合書階段 B 的方向）。
一致性有了，但低階裝置要付後製鏈的成本，而且沒有解決「天空的顏色管理是壞的」
這件事本身 —— 只是讓大家一起錯得一樣。

**方案 C**：維持現狀。不建議：同一個色表在兩條路徑上長不一樣，之後每調一次
天色都要調兩遍。

### ③ 材質與畫質升級書 第 1 章：從既有 canvas 貼圖自動生成法線／粗糙度貼圖

升級書的執行順序表裡，第 2 項（後製鏈全圖統一）已經在整合書階段 B 做掉了，
所以**第一個未完成項目是第 1 章**。做了：

**新檔 `src/world/texgen.js`**
- `normalFromCanvas(canvas, strength)` —— 把亮度當高度場，Sobel 求斜率轉法線。
  取樣座標取模而非夾邊：這些貼圖全是 RepeatWrapping 平鋪的，夾邊會在拼接處
  留下一圈假稜線。
- `roughnessFromCanvas(canvas, {min, max, invert})` —— 亮度重新映射成粗糙度。
  預設 `invert: true`（暗處＝凹紋／磨損＝比較粗），漆器那種亮處是高光的則關掉。
- `mapsFromTexture(tex, opts)` —— 吃**既有的 CanvasTexture**（`.image` 就是原本
  那張 canvas），所以既有的 `TEX.wood(1, 2)` 寫法原封不動就能升級，不必把每個
  draw 函式重新拆出來。repeat / wrap / anisotropy 會一起複製，三張貼圖的 UV
  必須完全一致，錯開一格就會「紋路對不上凹凸」。

**`main.js` 改了八個材質**（神社，其他圖一張都沒動）：
`wood` / `darkWood` / `plank` / `red` / `redFlat` / `stone` / `stoneBig` / `roof`。

升級書 §6 說「不要半調子混搭，同類物件要換就整類換」，所以 `darkWood`、`plank`、
`redFlat` 這三個雖然不在你原本列的五個裡面，還是一起換了 —— 它們跟 `wood`、
`red` 用的是同一種貼圖，只換一半的話柱子有木紋、地板沒有，比全都沒有更糟。

有了 `roughnessMap` 之後材質的 `roughness` 純量一律設成 1，粗糙度的絕對範圍
改由貼圖帶（兩者是相乘的，純量留在原值會把整體壓暗一階）。各材質的範圍以
原本的純量為中心往兩邊開，例如石頭原本 0.95 → `[0.86, 1.0]`。

順手修掉一個自己造成的 warning：`makeTexture()` 的 2D context 現在帶
`willReadFrequently: true`。這個旗標只在**第一次** `getContext` 時生效，
在讀的那一端補是沒用的（神社 console 從 8 個 warning 降到 0）。

**驗證**：語法掃描通過；神社開起來 console **0 error**；
`[texgen] 法線強度 1；自動生成 16 張資料貼圖；GPU 上的貼圖總數 62`
—— 一張色彩貼圖多帶兩張同尺寸的資料貼圖，總量在可接受範圍。

**留給你判斷（升級書 §5 規定的 A/B）**：法線強度三版截圖已放進 `shots2/`，
兩個近距離角度（石垣、拜殿木地板／柱），因為法線是表面級的東西，遠景看不出來：

```
shots2/tex-base-cu-masonry.png   ← 沒有法線貼圖（對照組）
shots2/tex-n0.5-cu-masonry.png
shots2/tex-n1.0-cu-masonry.png   ← 目前的預設值
shots2/tex-n1.5-cu-masonry.png
shots2/tex-base-cu-wood.png … 同上四張
```

不必改代碼就能自己換強度看：`index.html?nstr=1.5`（`nstr` 查詢參數，
預設 1.0）。定案之後把 `main.js` 的 `NORMAL_STRENGTH` 預設值改掉即可。

**為什麼停在這裡**：下一項是第 2 章（fBm 分層 noise，把貼圖從「顆粒」做成
「材質」），而它會**把上面那些 A/B 截圖裡的貼圖整個重畫**。兩件事疊在一起推，
你就分不出畫面的差別是法線造成的還是新 noise 造成的，強度也就沒得選了。
所以第 1 章的強度定案之後我再往下走 —— 你說一聲就繼續。
