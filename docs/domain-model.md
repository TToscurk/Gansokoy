# 地圖產生器・領域模型（詞彙表 + ADR）

這份文件是 `/grill-with-docs` 審查的產物。它存在的理由：
**最近八個回報 bug，每一個都是「缺少一個領域概念」的症狀**，
而不是各自獨立的實作失誤。

## 症狀 → 缺失概念對照

| 現象 | 缺的概念 |
|---|---|
| 建築離地浮空 | **地盤 Footprint** —— 建物該站在涵蓋範圍的最低點，不是中心點 |
| 樹長在建築裡 | **地權 Parcel** —— 誰佔了哪塊地；用圓形半徑判村界是湊的（村是長方形） |
| 河水埋在河床下 | **岸高 vs. 床高** —— 兩種地面高度被同一個 `height_at` 混用 |
| 鴨子橫著滑行 | **朝向軸 Facing Axis** —— glb 的頭朝 +X，程式假設 -Z，沒有約定 |
| 睡蓮浮到岸上 | **水體 WaterBody** —— 水面高度散落各處硬算，不是可查詢的物件 |
| 店前鋪面沒對齊門口 | **門面 Frontage** —— 建築不知道自己的門開在哪一面、哪個位置 |

根因：產生器是座標腳本（`gen_village.gd` 1200 行），三張圖各抄一份。
沒有模型只有數字 → 每蓋一張新圖就重新推導同一批概念、重踩同一批坑。
**剩下五張圖（竹林／永遠亭／無名之丘／太陽花田／神社）會讓成本乘以五。**

## 詞彙表（Glossary）

以下是提議的領域語彙。每個詞條標了「現在散在哪裡」。

### Terrain（地形）
- **BankHeight 岸高**：完全沒有開挖的自然地面高度。**水面高度一律用這個算。**
  現況：`gen_village.bank_h()`，只有村有，其他圖沒有。
- **GroundHeight 床高**：套用所有開挖（河、水路、池）之後的實際地面。
  物件擺放、碰撞、玩家踩的都是這個。現況：`height_at()`。
- **Carve 開挖**：對地形的減法（河床、池底）。現況：`river_carve` / `pond_carve`，
  但呼叫端要自己記得把它們加總進 `height_at`——漏一個就是一個 bug。
- **Footprint 地盤**：一塊矩形範圍的地面統計（最低點、高差）。
  建物站最低點、基石往下加深高差。現況：`_ground_under()`，**村內全部建物都走這條**
  （v8 補上了稗田邸／足洗邸／火見櫓），取樣密度隨尺寸走。
- **GroundSample 擺放高度**（v8 新增）：擺建物時該看到的地面。
  = 實際地面，但**水面以下不算數**。現況：`_ground_sample()`。
  這個詞是踩了兩次坑才長出來的：用 `height_at` 會讓院子裡有池塘的宅子沉到池底，
  用完全不開挖的 `bank_h` 又會讓水路旁的土塀浮在未開挖的岸高上。
  河床不算、岸坡算 —— 這是第三個概念，不是前兩個之一。

### Land（土地）
- **Parcel 地權**：已被佔用的矩形（建物、道具、樹）。查詢「這塊地能不能放東西」。
  現況：`_rects` + `_grid` 空間索引，只有村有；獸道與香霖堂各自用別的土法。
  v8 補上「水體也是不能佔的地」（原本只擋河與水路，池塘沒擋，長屋蓋進池裡）。
  `_claim()` 現在回傳索引，`_free_for_apron()` 可以「忽略自己那棟房子」。
- **Zone 分區**：村內／田環帶／村外，決定密度與可放什麼。
  現況：散落在各個 `if r0 < CORE` 判斷裡，**而且形狀跟實際村界不符**。
- **PathNet 路網**：折線集合，可查「離路緣多遠」「路面遮罩多少」。
  現況：三張圖各自複製一份 `_seg_dist` / `_path_info`。

### Water（水）
- **WaterBody 水體**：河、水路、池的共同抽象。要能回答
  「(x,z) 是不是水」「這裡的水面高度」「岸在哪」。
  現況：**仍然不存在**，但 v8 至少把「岸在哪」解出來了 ——
  `pond_shore_r()` 從開挖剖面反解水線半徑（水面 = 平面，岸線 = 地形剛好等於水面的那一圈）。
  「(x,z) 是不是水」目前散在 `_ground_sample()` 與 `_free()` 裡各寫一次。

### Building（建築）
- **Frontage 門面**：建築的哪一面朝街、門開在哪個位置。
  現況：**已實作** —— `_longhouse` 把每個玄關登記進 `_frontages`
  （世界座標、朝外方向、是不是商家、開間寬、地權索引）。
  同時修掉一個更根本的錯：立面永遠朝本地 +z，所以街區北側與西側的長屋
  **玄關是開向自家中庭的**。這才是店前鋪面永遠對不齊的原因。
- **Module 構件**：屋身／屋頂／玄關／窗／緣側。現況：全部寫死在 `_longhouse` 裡。

### Prop（道具與生物）
- **FacingAxis 朝向軸**：資產的正面朝哪個軸。**約定：一律 +X。**
  現況：口頭約定，錯了才發現（鴨子）。
- **ScatterRule 散佈規則**：密度、避讓、對齊。現況：每處手寫 while 迴圈。

## ADR-001：產生器要不要抽出領域模型？

**狀態**：**已定案 —— B. 邊蓋邊抽**（2026-08 審查）

**脈絡**：三張圖已完成，五張待建。八個回報 bug 全是缺概念造成的。
每張新圖現在要複製 ~300 行的地形／路網／散佈樣板。

**選項**：
- **A. 現在抽模型**：把上面的詞彙做成 gen_lib 的型別（Terrain / Parcel /
  WaterBody / Frontage）。三張舊圖回頭改用。成本：一輪不產出新地圖。
- **B. 邊蓋邊抽**：下一張圖（竹林）用新模型寫，舊圖不動，之後有空再回頭。
- **C. 不抽**：繼續複製貼上，靠回報修 bug。

**決定**：下一張新圖用新模型寫，舊的三張圖**不回頭改**。
理由：模型沒被真實地圖驗證過就先套用到三張圖，等於用猜的重構；
而且會有一輪完全沒有可看的產出。等新模型在一張新圖上證明可用，
再逐張把舊圖遷過去。

**推論**：`gen_lib.gd` 會同時存在「舊的自由函式」與「新的型別」一段時間。
新型別加在 `tools/model/` 底下，不動既有 API，舊圖不會被打斷。

## ADR-002：地圖該是「程式」還是「資料」？

**狀態**：**已定案 —— 維持程式**（2026-08 審查）

**決定**：地圖繼續是 GDScript。彈性優先——地圖的規則（密度隨方位變化、
街區用途表、地形函式）用資料描述會綁手綁腳，而且第一張圖的成本會暴增。
代價（只有改程式才能改佈局）用**地圖體檢工具**補：規則寫在程式裡，
但正確性由自動檢查把關。

現在每張圖是一支 GDScript，佈局寫死在程式裡（街道折線、街區座標、
建物尺寸都是 const）。另一條路是：地圖 = 一份資料（JSON/資源檔），
產生器是**通用的直譯器**。

- 資料化的好處：新圖不用寫程式；你可以在編輯器裡改資料就改佈局；
  地圖能被工具檢查（重疊、離地、孤島）。
- 代價：先要把「地圖描述語言」設計出來，第一張圖會更慢。

這個決定會影響上面 ADR-001 的抽法，所以要一起決。

## ADR-003：地圖體檢與可走性測試

**狀態**：**已定案 —— 兩個都做**（2026-08 審查）

**脈絡**：使用者回報的八個 bug 裡，有五個是「用眼睛看才發現」的幾何錯誤
（離地、穿模、壓街、浮空、錯位）。這些**全部可以自動檢查**。

**決定**：`godot/tools/check_map.gd` —— 載入任一張 .tscn，掃描節點樹，
輸出違規清單（含世界座標，方便在編輯器裡跳過去看）。檢查項目對應
每一個回報過的 bug：

| 檢查 | 對應的回報 |
|---|---|
| 建物底面 vs. 地形高度 | 「建築沒貼齊地面有離地的樣子」 |
| 樹／道具 的水平範圍與建物重疊 | 「有樹木長在建築裡」 |
| 物件中心落在街道遮罩上 | 「建築卡道」 |
| 水面 y vs. 該處地形 y | 「水是隱形的」「睡蓮浮到岸上」 |
| 傳送點之間可走 | 卡住、揉進建築、過不了橋 |

**推論**：產生器跑完自動接體檢；體檢有紅字就不算完成。
這也是「地圖維持程式」的配套——規則在程式裡，正確性由工具把關。

### 實作（2026-08）

```
godot --headless --path godot --script tools/check_map.gd -- all   # 幾何體檢
godot --headless --path godot --script tools/walk_test.gd  -- all  # 可走性
```

兩支都以 exit code 回報（有問題 = 1），可以直接接在產生器後面。

**體檢 `check_map.gd`** 讀 `.tscn` 的實際幾何，不重算 `height_at`——
要驗的是「場景長怎樣」而不是「產生器以為長怎樣」，否則產生器的 bug 會
同時騙過自己與體檢。檢查：建物離地／陷入、散佈物穿建物、水面埋在地下。

**可走性 `walk_test.gd`** 用**真正的碰撞體**跑：建 trimesh 碰撞（規則與
`main.gd` 相同）→ 射線找地面 → 每格放一顆玩家膠囊 → BFS 連通。
不看產生器的 `_rects`——產生器以為擋住的跟玩家實際撞到的是兩回事。

寫這兩支工具的過程本身就驗證了 ADR-003：**體檢第一版報了 41 個問題，
全是假的**（`global_transform` 在未進樹的節點上回傳單位矩陣，所有 AABB
塌到原點）。修好之後真正抓到的 6 個問題，每一個都對應到詞彙表裡缺的概念：

| 體檢抓到 | 缺的概念 | 修法 |
|---|---|---|
| 稗田邸／足洗邸離地 1.7~1.9m | **Footprint** | 特殊街區也改用 `_ground_under`，不再拿中心點高度 |
| 土塀整段離地 0.9~1.6m | **Footprint** 取樣密度 | 3×3 對 40m 長的牆太稀，改成每 4m 一點 |
| 長屋陷進自然池 2.8m | **Parcel** 沒有水體 | `_free` 除了河與水路，也要擋池塘 |
| 庭池 14%、自然池 8% 的水面埋在土裡 | **WaterBody 水線** | 水面半徑改由開挖剖面解出（`pond_shore_r`），不再直接拿 R |

另外兩個是修完 Footprint 才浮出來的**概念衝突**，記在這裡因為它們是
「同一個詞在不同脈絡意思不同」的典型：

- 稗田邸的院子裡有庭池 → 用 `height_at` 取 footprint 最低點會取到池底，
  整棟宅子沉 1.7m。
- 水路旁的土塀 → 改用完全不開挖的 `bank_h` 又會量到未開挖的岸高，浮 0.9m。

正解是第三個概念：**擺建物時的地面 = 實際地面，但水面以下不算數**
（`_ground_sample`）。河床不算、岸坡算。體檢那邊對應的調整是改用
第 15 百分位而不是絕對最低點，一格池底才不會讓整棟宅子被誤判。

### 順帶抓到的一類 bug：貼圖組不存在

`pbr()` 遇到不存在的貼圖組時，`load()` 只回傳 null，材質靜靜退化成純色。
「茅葺屋頂整片死白」「池邊的石頭像保麗龍碎片」都是這個——分別指到了
不存在的 `roof_thatch` 與 `cliff_rock`。現在 `pbr()` 會印警告。

**還有一個共用 Mesh 的坑**：`prop_mesh()` 直接改 glb 那份共用 Mesh 的
surface material，所以同一顆 `rock_*.glb` 只會留下**最後**設定的材質。
岩石一律走 `lib.rock_mat()`，不要各處各自指定。

## ADR-004：材質與資產的「靜默退化」要怎麼防？

**狀態**：**已定案 —— D. 材質也進體檢（指標式畫面檢查）**（2026-08 審查）

**決定**：畫面也要能自動檢查，但**只存指標、不存基準圖**。
固定機位算圖 → 抽出一組數字（平均亮度、過曝像素比例、色相分布、
邊緣密度、天空佔比、以及「albedo_texture 是 null 的材質」清單）→
寫進 JSON 比對。抓得到「屋頂死白」「整片發黃」「材質退化成純色」這類，
而且不會讓倉庫因為基準圖持續膨脹。

存基準圖（真正的畫面回歸測試）抓得更準，但每次正常的改動都要重建基準，
以每張 1.5MB × 多機位 × 多地圖來算，倉庫會被截圖淹掉。

*（機位組成、門檻值由我定；覺得不對再調。）*

**脈絡**：v8 花了兩輪才查出「茅葺屋頂整片死白」與「池邊石頭像保麗龍碎片」
的原因 —— `pbr()` 指到不存在的貼圖組（`roof_thatch`、`cliff_rock`），
`load()` 只回傳 null，材質靜靜退化成純色。

**這一類 bug 有兩個性質，跟 ADR-003 的幾何 bug 不同**：

1. **幾何是對的，只有「看起來」是錯的。** `check_map.gd` 完全不會抓到，
   `walk_test.gd` 也不會。體檢綠燈不代表畫面對。
2. **失敗是靜默的。** 沒有例外、沒有錯誤，只有一片白。使用者回報的
   「畫面整體看起來很白」有一部分就是這個，當時被歸因成光照設定。

同一類還有第三個：**`prop_mesh()` 改的是 glb 那份共用 Mesh 的 surface
material**，所以同一顆 `rock_*.glb` 只會留下最後設定的材質 —— 兩處各自
指定會互相洗掉，而且完全沒有徵兆。

**選項**：

- **A. 只加警告（v8 已做）**：`pbr()` 找不到貼圖組會印警告。
  成本最低，但只擋得住「打錯字」，擋不住共用 Mesh 那種。
- **B. 資產清單**：把「有哪些貼圖組／glb」做成一份清單，產生器啟動時
  先驗一遍，缺的直接 fail。要新增資產就得同步清單。
- **C. 畫面回歸測試**：固定機位算幾張圖，跟基準比對，差太多就 fail。
  抓得到所有「看起來不對」，但基準圖要跟著版本更新，而且需要 GPU。
- **D. 材質也進體檢**：`check_map.gd` 多掃一項 —— 場景裡有沒有
  「albedo_texture 是 null 而且不是刻意的純色材質」。介於 A 與 C 之間。

## ADR-005：下一個「排面感」的槓桿是什麼？

**狀態**：**已定案 —— A. 角色先行（當作方向驗證）**（2026-08 審查）

**決定**：下一輪做**一個角色**丟進現在的村子。不是因為角色最重要，
而是因為「寫實環境 × 卡通角色」這個方向**從來沒被驗證過**，而它是
整個美術路線的前提。驗錯了，先做完的植被要重做。

範圍（我定的）：簡版靈夢 —— 造型優先，加骨架與一個走路循環。
只做 T-pose 站著驗不出東西；真正要看的是「卡通人物在寫實街景裡動起來」
是什麼質感。不接控制器（那是下一步）。

**脈絡**：使用者最早點名的不滿有四項 —— 角色的設計感、地圖的排面感、
材質不夠真實、太模組化。到 v8 為止：

| 不滿 | 進度 |
|---|---|
| 材質不夠真實 | PBR 地形／建材、Blender 有機資產、水面 shader —— 做了不少 |
| 太模組化 | 部分：立面逐間做、屋頂有切妻、街區有變化 |
| 地圖的排面感 | 只做了三張原生圖，其餘 16 張是 blockout 或未建 |
| **角色的設計感** | **零。玩家還是一顆膠囊。** |

v8 這一輪全部是**正確性**（幾何 bug、可走性、材質退化）。正確性不會
變成排面感 —— 現在的俯瞰圖幾何全對，但看起來還是模組化的：
低模樹團、每棟長屋剪影幾乎一樣、院子空的、街上沒有人。

**選項**（可複選，順序才是重點）：

- **A. 角色**：使用者最早點名、也是唯一完全沒動過的項目。
  Blender 管線已經能雕龍與鳥，做人物是同一條路。
- **B. 植被**：寫實葉片卡樹、灌木層、地被。三張原生圖同時受惠，
  也是俯瞰圖裡「模組感」最大的來源。
- **C. 第四張圖（竹林）**：原生圖從 3/19 變 4/19，也是新模型的試驗場。
- **D. NPC 與生活感**：`walk_test.gd` 已經產出一張可站立格點圖 ——
  那本來就是 navmesh 的前身，接上去 NPC 就不會撞牆（使用者最早的抱怨之一）。

**未決的配套問題**：五張 blockout 圖（竹林、永遠亭、無名之丘、太陽花田、
神社）跟原生圖之間有明顯的品質斷崖。是照順序逐張換掉、先給每張套統一的
地形與光照、還是暫時鎖住未完成的圖？

## ADR-006：專案的終點是「有玩法的遊戲」

**狀態**：**已定案**（2026-08 審查）

**決定**：這不是風景遊覽，最終要有玩法。

**這條決定的連鎖後果（重要）**：

1. **地圖規格從此由玩法反推，不再由「好看」決定。**
   現在的人間之里是照好看蓋的：街 11m 寬、街區封閉、建築不能進去、
   沒有制高點、沒有可互動的門。這些在不同玩法下是不同的答案 ——
   彈幕要開闊場地與乾淨背景，探索要能進室內與秘密路徑，
   對話任務要每個商家有主人、每個玄關是真的門。
2. **「人里做到底」現在做不完** —— 因為還不知道要做到什麼底。
   v8 的收尾只能算「視覺上的收尾」，玩法層的收尾要等規格出來。
3. **ADR-001 的報酬率下修**（見下）。

**推論**：玩法類型未定之前，優先做「不論哪條路都用得上」的東西 ——
角色、植被、工具、NPC 尋路。避開只有某一條路才划算的投資
（例如為彈幕重排街區、為探索做整套室內）。

## ADR-007：廣度 vs 深度 —— 少數幾張做到底

**狀態**：**已定案 —— 深度優先**（2026-08 審查）

**決定**：集中做少數幾張，其餘暫時不動。排面感來自深度，不是張數。

- `godot/blockout/` 的 300MB 底稿目前是在「假裝世界很大」。
  暫時留著（未完成的圖還要靠它），但它不是資產，是鷹架。
- 19 張圖的 `mapRegistry` 維持不變 —— 連通關係還有用，
  只是大部分節點會長期停在底稿狀態。

## ADR-001 補記：報酬率下修（2026-08 第二次審查）

原本抽領域模型的理由是「剩下 16 張圖會讓成本乘以 16」。
ADR-007 定案深度優先之後，剩下的新圖只有 2~3 張，抽模型的報酬率大幅下降。

**修正後的立場**：不再為了「服務 16 張圖」而抽。但這一輪（v8）證明了
另一個理由仍然成立 —— **同一個概念缺失會在同一張圖裡重複咬人**
（Footprint 在長屋修好了，稗田邸／足洗邸／火見櫓又各犯一次；
Parcel 擋了河與水路，忘了池塘）。

所以抽模型的目的從「跨圖重用」改成「**同圖內一致**」：
把 Terrain / Parcel / WaterBody / Frontage 變成**一定會被走到的路徑**，
而不是每個街區函式自己記得要呼叫。優先度低於角色與玩法原型。

## ADR-008：效能 —— 原生圖不要重複做碰撞

**狀態**：**已定案**（2026-08 審查）

**脈絡**：使用者回報「有點卡」，並提議「每張地圖的世界地形能再小一點」。
量了之後發現真正的浪費不在地形大小：

| | 之前 | 之後 |
|---|---|---|
| 人間之里的 trimesh 碰撞體 | **2262** | **1**（只有地形） |
| 場景自帶的手做碰撞箱 | 458 | 458（不變） |

`main.gd` 原本不分青紅皂白地掃全場，替每一片跨度 ≥6m 的 mesh 生
三角網碰撞體 —— 包含每一片屋頂、每一段牆、每一塊基石。而原生圖的建物
早就自己放好碰撞箱了。等於在 458 個箱子上面又疊了 2262 個三角網。

**決定**：`own_colliders` 的原生圖只有 `Terrain`（與明確標了
`needs_trimesh` 的節點）做 trimesh，其餘靠場景自帶的碰撞箱。

**推論 / 教訓**：這條規則 `walk_test.gd` 必須同步 —— 測試如果用跟遊戲
不同的碰撞規則，測到的就不是玩家會撞到的東西。改完立刻被自己的工具抓到
一個真的漏洞：**石垣護岸原本只靠 trimesh 擋人**，拿掉之後可以直接穿牆
走過水路（「要過橋」那條路線從 46260 格掉到 368 格）。護岸補上碰撞箱後恢復。

地形尺寸暫時不動（600×600）—— 先看這一刀夠不夠。不夠的話下一步是
把散佈物件的 LOD / 可見距離接上，而不是縮地圖。

## ADR-009：角色 —— Q 版、不綁骨架、部位獨立

**狀態**：**已定案**（2026-08 審查，ADR-005 的實作決定）

**決定**：
1. **Q 版約 3.5 頭身**，不是寫實比例。用程式雕寫實人體會翻車，Q 版容錯高。
2. **不綁骨架**。各部位（Body / Head / ArmL / ArmR / LegL / LegR）在 glb 裡是
   **獨立物件、樞紐擺在關節上**，走路動畫在 `scripts/npc.gd` 裡轉節點。
   Q 版四肢是硬管，蒙皮沒有意義，而且省掉「產生器要輸出動畫資料」整條管線。
3. **五官要投影到臉的表面上**。這點踩了三輪：頭是 x 半徑 = HEAD_R 的橢球，
   把眼睛擺在「臉前面一點」（0.70·R）其實是埋在頭裡面 —— 眼睛所在的高度與
   左右偏移代進橢球方程式，臉皮只在 0.92·R。現在有 `face_x()` 幫忙算。
4. **頭髮用「一顆球依髮際線裁面」**，不要拿好幾顆球去拼瀏海。
   拼出來的結果是：v1 一張被白邊框住的面具、v2 一條橫在臉上的黑布條。

**配套**：`tools/gen_charpreview.gd` 產一張角色打樣場（中性地面、
1.7m 身高尺、正面與側面各一排）。角色一放進村子就會被 npc.gd 帶著走、
街景的光照又會干擾判斷，所以要有專用的看板。

## ADR-010：人間之里的佈局要重做 —— 窄巷 + 有機聚落

**狀態**：**已實作但已回滾**（2026-08）。
分析（街太寬、方格太整齊）仍然成立，但實作出來的版本使用者不滿意，
已 revert 回方格佈局。下次要重做的話，問題出在**密度**：
沿街排屋有五成的位置因為互相排擠放不下，村子攤成郊區而不是變擠。
街寬本身（8m / 3~4m）不是問題所在。

**脈絡**：「太模組化」一直被當成材質與資產的問題在修。實際看了街景照片
之後，真兇是**佈局的兩個數字**：

1. **街太寬**。本通 11m、橫町 9m、其餘 7m。真實日本村落巷道是 **2~4m**，
   宿場町的主街也只有 6~8m。11m 是現代馬路。
   街一寬 → 建築被推遠 → 街景空曠 → 像模型展示場。
   而且它是連鎖的：街寬 → 街區得大（42×45m）→ 房子散 → 要靠土塀補空缺
   → **每個街區外圍一圈土塀**，那正是俯瞰圖裡最模組的東西。
2. **6×7 完美方格**。`BLOCK_X` 六個等距、`BLOCK_Z` 七個等距，是最初隨手訂的，
   之後沒人動過。真實聚落沿地形、水路、舊路長出來，不會是方格。

**決定**：
- 主街降到 **8m**，巷道 **3~4m**。
- 街區改成**有機生長**：大小不一、街道略微彎曲、沿水路與地形長。

**推論**：這是大手術。`PATH_SEGMENTS` 是 `_path_info` / `_free` /
店前鋪面 / 村民路線 / 地面遮罩的共同來源，動它等於動整張圖。
體檢與可走性測試在這時候才真的派上用場 —— 重排完要能證明「還是走得通」。

## ADR-012：場景的四個缺口

**狀態**：**已定案 —— 四項全做**（2026-08 審查）

使用者同時註明「不用顧慮系統規格了」。對照上一輪的「有點卡」，
這裡的解讀是：**視覺密度優先，效能用工具管而不是靠自我節制。**
ADR-008 的碰撞修正（2262 → 1）已經買回餘裕，FPS 與物件數要進畫面檢查
（ADR-004）一起量。

1. **能進去的室內** —— 109 棟長屋沒有一棟能進。玩法要有互動就得先有門。
2. **生活感雜物** —— 曬衣、柴堆、水桶、農具、掃過的痕跡。現在的村子太乾淨。
3. **建築的變化度** —— 每棟長屋剪影幾乎一樣。要不同層數、不同屋頂形式、
   有的傾斜有的老舊。
4. **植被層次** —— 低模樹團是俯瞰圖裡另一個模組感來源。寫實葉片卡樹、
   灌木層、地被。

**順序**：佈局（ADR-010）先做 —— 建築變化、雜物、室內全部掛在建築上，
而建築的位置會因為重排而全部改變。植被層次與角色比例（ADR-011）
跟佈局無關，可以並行。

## ADR-013：v9 有機佈局回滾

**狀態**：**已回滾**（2026-08）

v9 把街道網改成執行期生成（本通 8m 緩彎、巷道 3~4m、沿街排屋）。
使用者看過之後不滿意，要求回上一版，已 `git revert`。

**保留下來的**（跟佈局無關，都是真的 bug 修正）：
- `check_map.gd` 直接解 `mm.buffer` —— 散佈物檢查原本**一直是假綠燈**
- 4.5 頭身的角色（ADR-011）
- 碰撞效能修正（ADR-008）

**回滾後靠修好的體檢立刻抓到三個舊 bug**（方格版本一直都有，只是檢查是假的）：
1. `_build_trees` 的佔位檢查只在 `r0 < CORE` 時做 —— **CORE 是圓的、村是長方形的**，
   南北兩排街區落在圓外，那幾排的院子長出穿進建築的樹。
2. `_wall_run` 從來沒有 `_claim` —— 岸石／樹會直接長在土塀上。
3. `_wall_run` 是「街區缺口一律補上」的，不像建物會先問 `_free`，
   於是村西南街區的圍牆直接橫過自然池。

**另外修掉一個載入錯誤**：`char_scene` 原本 instantiate glb 之後把子節點設成 owner，
存 .tscn 時節點被存兩次（`instance=ExtResource` + 明確子節點），
在編輯器開場景會噴一整排「匯入的節點名稱與現有的衝突」。
改成把 mesh 與 transform 抄出來、掛在新建的節點上。

## ADR-014：桁架／骨架類幾何一律用「端點」定義，不要手算旋轉

**狀態**：**已定案**（2026-08）

**脈絡**：火見櫓被使用者點名「設計不良」。看了截圖才發現柱子根本沒接起來 ——
v9 的做法是「每層各自放四根傾斜的圓柱」，每層的傾角是各自算的，
層與層之間對不起來，遠看像散掉的鷹架。

**根因**：這類結構我一直是「算好中心點 + 兩個歐拉角」再擺一根圓柱。
只要有錐度（塔是外八字的）或分層，那組數字就一定會對不齊 ——
而且錯了不會有任何錯誤訊息，只會變醜。

**決定**：`lib.strut(parent, name, a: Vector3, b: Vector3, r, mat)` ——
**給兩個端點，位置與旋轉由程式算**。桁架、斜撐、欄杆、梯子、吊繩全部走這個。
接點吻合是幾何保證的，不是我算對的。

**推論**：這條規則的適用範圍比塔大得多 —— 橋的桁架、鳥居的貫、
棚架、繩索、任何「從 A 連到 B」的構件。以後看到 `cyl(...) + rotation.x/z`
在描述一根斜的東西，就是該換成 strut 的訊號。

## ADR-015：形狀的「規則」要寫成常數，不要藏在座標裡

**狀態**：**已定案**（2026-08）

**脈絡**：使用者要求「水道直直的就好不要轉彎」。v10 為了接到大河，
把水路東端拐了個彎 —— 那個折角在編輯器裡一眼就看到。

**決定**：水路是**一條直線**（固定 z=85，一路拉到 x=236 穿過河）。
大河在 z=85 附近的中心線約在 x=225，所以直直拉過去自然就接上，不用轉彎。

**教訓**：我當時是「把端點挪到河邊」——那是在座標上補一刀，
而不是承認「這條水路的規則是直線」。規則寫成常數（一條 z），
之後任何調整都不會不小心把它弄彎。
